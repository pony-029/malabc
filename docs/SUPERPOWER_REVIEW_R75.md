# R75 复盘：拿整棵 Linux 内核语料测 malabc 的 C 前端

> 本轮的任务不是「加门」，而是**把工具推到真实世界语料的极限上看它到底怎么样**。
> 语料：Linux **6.19.14** 完整源码树（sha256 已对镜像参考哈希校验一致）。
> 规模：**62,704 个 C 系文件 / 36,155,901 行**。
> 结论先说：**跑得动、跑得完、跑得对**（全树一把梭 661 秒、峰值 10.8 GB、rc=0、零崩溃），
> 但**判据精度在真实内核代码上崩了**——本轮量化出 `c_missing_return` 在四个子系统上
> **假阳性 85%~100%**，并逐条取到**五个真缺陷**的根因，其中三个已修好并两向验证。

### 3.3 内存模型（用于判断"多大机器能跑"）

以最大两个尺度点拟合：**峰值(MB) ≈ 0.298 × 千行 + 24**
⇒ 36.2M 行预测 **10.5 GB**（实测 10.80 GB，模型误差 <3%）。
**含义**：全树一把梭需要 **≥16 GB 物理内存**（本轮机器 31.7 GB / 可用 13.2 GB，跑完还剩 ~2.5 GB 余量）；
16 GB 机器应当**按顶层目录分批**跑（最大批 `drivers` 只要 5.8 GB）。

### 3.4 一条容易忽略的坑：**换运行范围，读数就变**

| | 逐目录跑（求和） | 整树跑 |
|---|---|---|
| 调用边 | 2,427,644 | **7,065,831** |
| `c_unused_static` | 249,477 | **230,066** |

同一棵树、同一份代码，只因为「一次分析的范围」不同，调用边差 **2.9 倍**、
`c_unused_static` 差 **19,411 条（8.4%）**。
⇒ 报告里写「函数 X 未被调用」时，**必须同时说明分析范围**，否则这句话没有意义。

## §4 告警构成：1,314,443 条里真正值钱的是极少数

| 判据 | 条数 | 占比 |
|---|---|---|
| `c_missing_doc` | 560,718 | **42.7%** |
| `c_uninit_pointer` | 458,329 | **34.9%** |
| `c_unused_static` | 249,477 | **19.0%** |
| `c_missing_return` | 33,273 | 2.5% |
| `c_too_many_params` | 7,789 | 0.6% |
| `c_missing_guard` | 2,029 | 0.2% |
| `c_buffer_overflow` | 1,230 | 0.1% |
| `c_use_after_free` | 657 | 0.05% |
| `c_array_oob` | 636 | 0.05% |
| `c_double_free` | 305 | 0.02% |
| **合计** | **1,314,443** | 100% |

**三条判据占了 96.6%**。而它们恰好都是**低信息量**的：
`c_missing_doc` 是风格（内核对内核文档有自己的规范，不要求每函数带注释）；
`c_uninit_pointer` 是"声明了指针又解引用"的文本配对，在 C 里几乎必然成立；
`c_unused_static` 受分析范围影响（§3.4）。
真正有安全含义的 `c_use_after_free` / `c_array_oob` / `c_double_free` / `c_buffer_overflow`
合计只占 **0.22%**。

> **这一节的结论比任何单条告警都重要**：在大语料上，**"告警总数"不是质量指标**。
> 没有假阳性率，1,314,443 这个数字既不说明工具好，也不说明代码差。

## §5 五条真缺陷（全部有最小复现与根因）

取缺陷的方法不是"看告警猜"，而是三步：
① 抽出可疑告警 → ② **回到内核源码逐字核** → ③ **写最小对照实验**把变量隔离到只剩一条。

### B1 `c_missing_return` 的 void 判据漏掉限定词 / GCC 属性 —— 已修

`matlabc.py:8327` 原判据：

```python
not ret.startswith(("void", "static void"))
```

内核里 void 函数**几乎从不**写成裸 `void` 或 `static void`：

```
static inline void                              2261 个函数
static __always_inline void                      134
__bpf_kfunc void                                  71
static noinline void                              66
__no_kcsan static void                            33
static __init void                                28
asmlinkage __visible void __softirq_entry        （softirq.c）
notrace void __weak                              （stop_machine.c）
```

**全部**被这条 `startswith` 判成「非 void」⇒ 只要函数体里没有 `return`，就报「非 void 函数无 return 语句」。

### B2 `_func_body_lines` 的 1-based / 0-based off-by-one —— 已修

```python
return lines[def_line:end]      # def_line 是 1-based，却被当 0-based 下标用
```

等价于**跳过定义行**。对「单行函数」（头文件里大量存在）函数体直接落空或只剩下一行
空行 ⇒ `return` 计数为 0 ⇒ 凭空报缺陷。

**最小复现**（`_kernel/exp2/m1.c`，全文两行）：

```c
static int one(void) { return 1; }
int two(void) { return 2; }
```

修复前：`two` 被报「非 void 函数 two 无 return 语句」——**它有 return**。

### B3 行文本被 `c_missing_doc` 门控 ⇒ 四个判据**静默漏报** —— 已修

`matlabc.py:8248`：

```python
lines = _c_lines_effective(pf.get("path")) if _on("c_missing_doc") else []
```

而下面 `c_uninit_pointer` / `c_array_oob` / `c_use_after_free` / `c_missing_return`
**全部**靠 `lines` 取函数体。于是只要用户没有同时开 `c_missing_doc`，这四个判据
**一条都不产出，且不报错**。实测同一目录：

| 调用 | 报出条数 |
|---|---|
| `--checks c_missing_return` | **0** |
| `--checks all` | **3** |

这是**静默假阴性** —— 比假阳性更危险的一类缺陷。
（代码在 `c_double_free` 那一支里**已经**写了注释警告这个坑并绕开了，但同一段里
另外四个判据没有跟着改。）

### B4 调用出现在 `(` / `,` / `&` / `*` 之后被判成「强转」丢弃 —— 本轮记录，未修

`matlabc.py:7604-7606`：

```python
prev = line[max(0, cm.start() - 1):cm.start()]
if prev in ("*", "&", "(", ","):
    continue
```

本意是跳过 `(int)x` 这种强转，但 `if (foo())` / `while (foo())` / `for (; foo(); )`
里 `foo` 前面**正好就是 `(`** ⇒ 调用边被丢掉。

**最小复现**（`_kernel/exp/probe_c.c`，只改"调用出现的语法位置"这一个变量）：

| 函数体 | 调用边是否建 |
|---|---|
| `{ target(); return 0; }` | ✔ |
| `{ return target(); }` | ✔ |
| `{ int x = target(); return x; }` | ✔ |
| `{ return target() + 1; }` | ✔ |
| `{ int x = 0; x = target(); return x; }` | ✔ |
| **`{ if (target()) return 1; return 0; }`** | **✘** |
| **`{ while (target()) break; return 0; }`** | **✘** |
| **`{ for (; target(); ) break; return 0; }`** | **✘** |

**后果**：`c_unused_static` 会把这些"只在条件里被调用"的 static 函数报成"项目内未被调用"。
内核实例：`fs/ext4/balloc.c:74` 的 `ext4_block_in_group` 在第 136/145/212/216/222 行
被调用 6 次，**全部在 `if (...)` 条件里** ⇒ 被判"未被调用"。

### B5 多行宏把返回类型字符串污染 —— 本轮记录，未修

`drivers/net/can/gw.c` 的 `mod_and_fddata` 之类，函数定义前有一大段跨行宏调用，
返回类型抽取把**前面宏的整段文本**一起吃进来：

```
ret = 'MODFUNC(mod_and_id, cf->can_id &= mod->modframe.and.can_id)
       MODFUNC(...) ...  static void'
```

这类 `ret` 字符串里混入了 `*`（来自宏实参），任何基于 `ret` 的判据都无法正确分类。
本轮 4 个子系统修复后残留的 10 条里有 **5 条**是这一类。

## §8 诚实边界（本轮**没有**解决的事）

1. **B4（条件里的调用丢边）未修**：它的影响面比 B1/B2/B3 都大（涉及调用图与
   `c_unused_static`），修法要区分「真强转 `(TYPE)expr`」与「括号里的调用 `(foo())`」，
   必须再配一轮两向验证 —— 本轮只把它**取证到根因级**，不敢顺手改。
2. **B5（多行宏污染返回类型）未修**：需要改返回类型抽取的词法层。
3. **`c_uninit_pointer` 458,329 条未做假阳性量化**：本轮只量化了
   `c_missing_return` 与 `c_unused_static` 两条。其余判据的假阳性率**未知**，
   因此 §4 的"占比"**不能**被读成"缺陷密度"。
4. **`__noreturn` 语义未识别**：`static int` 但以 `do_exit()` 结束的函数仍会被报。
5. **逐目录跑 ≠ 整树跑**（§3.4）：本报告两套数字都给，不给单一结论。
6. **`kthread.c:380 kthread` 那一条我还没解释清楚**：它在 380~435 行内有 7 个 `return`，
   却仍被报「无 return 语句」。可能是 `funcs` 列表里有更靠前的条目把 `end` 截断，
   需要再单独取证。**未定就写未定。**
7. **语料是 tarball，不含 Git 历史**；本轮结论只覆盖 6.19.14 这一个版本。
