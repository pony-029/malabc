# 工程级算法降维平台 —— 与现有底座融合方案（设计，不含代码）

> 输入：产品愿景五层体系（工程图谱 → 配置编排 → MIR 降维 → C 脚手架 → 运行时托管）
> 约束：**产物仍是 C**（不改成 Rust）；本轮只设计、不写代码。
> 方法：先核事实，再定优先级；每个阶段必须带可机器判定的验收口径。

---

## 一、先核事实：五层里**已经有多少**

不核事实就排期，会重复 R681（做了局部 struct，翻转 0 个）与 R720（以为工程能跑，实际 `unimplemented`）的错误。

| 愿景层 | 现有底座 | 状态 |
|---|---|---|
| L1 工程解析/图谱 | `translate/project_map.py`、`tools/build_module_graph.py`（产出 mermaid，含 edges） | **有**，但只到"看"，未参与生成 |
| L2 配置编排 | `m2c.project.json`（存在）、`tools/mlc_project.py`（含 ram/budget 字样） | **有雏形**，扁平、无继承 |
| L3 MIR 降维 | `mir.py`（前端）、`hir.py`（HIR 解析+降级）、`vm.rs`（解释器） | **强**（语料 58/58、HIR 往返 56/56） |
| L4 C 脚手架 | `rust/m2c/src/project.rs`：CMakeLists / include/`proj.h` / src/gen.c / 每函数 .c / main.c / selftest.c | **强**（实测 gcc rc=0） |
| L5 运行时托管 | `c_runtime`（静态池）、q15 定点、Rust VM | **有** |

**结论：五层里约 60% 的零件已经存在，缺的不是层，是"层与层之间的接线"。**

## 二、唯一的硬断点：跨文件调用（必须先修）

R720 实测（3 函数工程 `driver → twice → scale`）：

```
mir.py <目录>   ✅ 三个函数进同一份 MIR，跨函数调用记为 call:
m2c build       ✅ 产出完整 C 工程（CMake/include/gen/每函数 .c）
gcc             ✅ rc=0
运行            ❌ driver / twice → UNIMPLEMENTED，只有无调用的 scale 正确
```

生成的 C 里直接写着病因：

```c
/* TODO(call): scale 不是本文件里已生成的函数 */
return MLC_UNIMPLEMENTED;
```

而 `driver_m.c` 里的 `m2c_twice(x, y)` 是**正确生成**的 —— 同一工程内**部分**能解析、部分不能。

**判断：这不是"函数级转义"的问题，是"工程级符号可见性"的问题。** 图谱、配置、预算全都建立在这条链能跑之上，所以它必须是第 0 步。

## 三、融合方案：一条流水线，五个决定点

```
MATLAB 工程目录
   │
   ├─①工程解析──────► 模块图 / 调用树 / 数据流        （project_map + build_module_graph）
   │                     └─ 决定点 A：模块怎么切
   ├─②配置编排──────► 三层配置合并 → 一份**生效配置** （project → module → function）
   │                     └─ 决定点 B：配置在哪里生效（唯一 reader）
   ├─③语义降维──────► MIR（可经 HIR）                （hir → mir）
   │                     └─ 决定点 C：降到哪一档（浮点/q15/静态形状）
   ├─④工程生成──────► C 工程 + api.h + CMake         （project.rs）
   │                     └─ 决定点 D：符号可见范围（跨文件 call）
   └─⑤四路哈希差分──► 数值必须与原始 MATLAB 一致
                         └─ 决定点 E：差异算谁的（打印/表示/真算错）
```

### 决定点 A：模块怎么切

**不要**按文件机械切（一个 `.m` 一个 `.c` 已能做，但没有"大模块"概念）。
按**调用连通分量 + 数据流边界**切模块：一个 module = 一组强连通函数 + 一个 `module.json`。

理由：用户明确要求"C 的大模块也需要管理"。文件级只能给出 2000 个 `.c`，模块级才能给出"这一个算法 = 1 个 `.c` + 1 个 `.h` + 1 份预算"。

### 决定点 B：配置在哪里生效（**这是本方案最关键的一条**）

项目里已经吃够"声明了但不生效"的苦：R675（算子表条目不被 `parse_line` 读）、R703（`A(:)` 的 sample 被当成函数名）。

**因此配置模型的第一条不是继承，而是"唯一生效点"。**

```
project.json  ─┐
module.json   ─┼─► 合并（深合并，后覆盖前） ─► **生效配置** ─► MIR 的 arg:/var:/fill: 行
function 注解 ─┘        （唯一 reader）              （唯一消费点）
```

判据（必须是机器可判的）：**同一工程，改一处配置，只有对应的 MIR 行变化**；
且全仓只允许**一个**函数读配置文件（grep 可判）。

### 决定点 C：降到哪一档

三档并列，由配置选：

| 档 | 值模型 | 判据 |
|---|---|---|
| `f64` | 现状（默认） | 语料 58/58 |
| `q15` | 定点 + 溢出/舍入策略 | 与 f64 结果在给定容差内 + 溢出必须**报告**不静默饱和 |
| `static-shape` | 全部形状在编译期确定 | 无注解即拒绝（现状边界） |

**要点**：q15 不做"自动转换"，只做"显式声明后转换"。否则精度损失会变成不可归因的错误。

### 决定点 D：符号可见范围

跨文件 call 分三种，必须分别处理（不能一刀切）：

| 情形 | 处理 |
|---|---|
| 被调函数**在本工程内且可生成** | 直接调用 `m2c_<name>`（R720 已能做一半，要补全） |
| 被调函数**在工程内但不可生成** | 生成**契约桩** `m2c_ext_<name>`：声明 + 返回 `MLC_ERR` + 一句人话原因；**其余函数照常可用** |
| 被调函数**不在工程内**（外部依赖） | 同上，且写进 `api.h` 的 external 清单 |

这是抄 MATLAB Coder 的 `coder.extrinsic` 思路（`DESIGN_CODEGEN_LESSONS.md` §2），
要点是：**局部失败不拖垮整个工程**。

### 决定点 E：四路哈希差分

已有的四条执行路径，统一到**同一种可比对象**：

| 路径 | 现状 |
|---|---|
| Octave 跑原始 `.m` | 有（可选依赖） |
| Rust VM 跑 MIR | 有（58/58） |
| C 跑生成物 | 有 |
| 回译 `.m'` 跑 | 有（58/58） |

统一口径：**IEEE-754 位模式哈希**（R719 已建立），并在比对前把"表示差异"排除掉
（打印格式、`-0/+0`、NaN 符号位 —— R719 已抓到两处这类假红）。

## 四、内存预算模型（用户特别强调的一项）

现状：`c_runtime` 有静态池，`mlc_project.py` 有 ram/budget 字样，但 **`project.rs` 生成时不感知预算**。

设计：**预算在生成期判定，不留到运行期 OOM。**

```
单个函数峰值 = Σ(所有 arg/var/fill 的静态元素数 × 类型宽度) + 临时量峰值
                     ↑
              MIR 里全是静态形状（前提：有形状注解）
工程峰值 = 模块内函数的峰值之和（同一模块顺序复用池）+ 模块间不共享的部分
```

三条硬规则：

1. **推不出就拒绝**：任一变量无静态形状 → 不参与预算 → 报"该函数无法计算预算（第 N 行）"，
   并给出 `% @m2c shape` 建议（复用 `check --annotate`）。
2. **超预算在生成期报错**，错误信息必须包含：函数名、变量名、需要多少、还剩多少。
3. **预算进产物**：`budget.json` 随工程输出，`CMakeLists.txt` 里以宏固化（`M2C_POOL_BYTES`）。

> 为什么不在运行期检查：嵌入式板上"能编过但一跑就 OOM"是最差的一种交付。
> 生成期能算出来的东西，不该留给板子去发现。

## 五、AI 层（L2 的"动"与"静"）—— 放在哪、不放在哪

| 放 | 不放 |
|---|---|
| **生成候选配置**（读代码语义 → 提议 shapes/类型/模块切分） | 直接决定"能不能转" |
| **解释超预算的成因**（哪个函数、哪个变量） | 修改 MIR / 生成 C |
| **把 check 的拒绝理由翻译成人话 + 改写建议** | 成为第五份"支持定义" |

硬约束（沿用 R690 对 MCP 的规矩）：**AI 层的所有判断必须落到既有的确定性工具上
（`check` / `task_kpi` / 预算计算器），不得自己实现一套"支持判定"。**

## 六、分阶段计划（每阶段一个可机器判定的口径）

| 阶段 | 内容 | 轮次 | 验收判据（**工程级**） |
|---|---|---|---|
| **P0 打通调用** | `emit_func` 的 `known` 可见范围 → 跨文件 call | 1 | 3 函数工程运行正确；语料 58/58 不回归 |
| **P1 配置唯一生效点** | 三层配置合并 + 只有一个 reader + `module.json` | 1~2 | 改一处配置 → 只有对应 MIR 行变化；grep 证明 reader 唯一 |
| **P2 预算模型** | 静态峰值计算 + 生成期报错 + `budget.json` | 1~2 | 给定 64KB，超限工程报错并指名函数/变量；不超限的工程 `gcc` 后运行不 OOM |
| **P3 契约桩** | 不可生成函数 → `m2c_ext_*` + `api.h` 清单 | 1 | 含 1 个不可生成函数的工程**仍能编译并跑通其余部分** |
| **P4 图谱接配置** | 模块图节点 → 直达 `check --annotate` / 配置建议 | 2 | 图上每个节点都能给出"该配什么"，且建议被采纳后复扫有变化 |
| **P5 HIR 接管** | `--via-hir` 逐函数接管 | 2 | 接管比例上升过程中三段对拍恒 58/58 |
| **P6 四路哈希进 CI** | 位模式哈希 + 表示差异归一 | 1 | 无 Octave 机器上四路仍成立 |

**止损线**：P0 若一轮内无法让 3 函数工程跑通，**停止后续所有阶段**，先把它定位清楚 ——
因为 P1~P6 的价值全部建立在"工程能跑"之上。

## 八、第一个工程级判据（建议立刻写）

现有 41 道门全是**函数级或语法级**。缺一条最朴素的：

```
给定 examples/proj_demo（3 函数互相调用）
  → m2c 生成工程
  → gcc 编译
  → 运行
  → 输出必须等于 手算值（driver(1,2,3) = 12）
```

这条判据今天会红（R720 实测 `unimplemented`），而这正是它的价值：
**它把"工程能跑"从口号变成红灯。**

### P0 实测（2026-11-11）：**单实参已通，字面量实参未通**

本文档原先写着"这条判据今天会红"（基于 R721 的实测）。三十多轮之后它**部分绿了**：

| 形态 | 例子 | 状态 |
|---|---|---|
| 单实参跨文件调用 | `combine → addone / scale2` | ✅ 跑出 `4 8 12`（判据：`tests/test_project_level.py`） |
| **字面量实参**跨文件调用 | `twice → scale(x, 2)` | ❌ `TODO(call)` + `MLC_UNIMPLEMENTED` |

**根因（`rust/m2c/src/emit.rs` 约 1335 行）**：

```rust
for a in args {
    match f.var_dtype(a) {
        Some(dt) if ... => { ... }
        Some(_) => call_args.push(ident(a)),
        None => { ok = false; ... }   // ← 字面量 `2` 走这里
    }
}
if !ok { /* 发 TODO(call) 并 return MLC_UNIMPLEMENTED */ }
```

字面量没有 dtype ⇒ `ok=false` ⇒ 整条 call 被放弃。
修法方向：字面量按**被调函数形参类型**处理（标量形参直接写字面量；
`mlc_array` 形参需要先落一个 1 元临时量）。

**欠账是具名的**：`test_literal_arg_cross_file_call` 用 `xfail(strict=True)` 登记 ——
一旦修好，它会 XPASS 并让测试套件变红，强制摘掉标记（不允许欠账悄悄变绿）。

### P1 现状（2026-11-11）：**配置模型完整，但没有接线到生成器**

| 环节 | 状态 | 证据 |
|---|---|---|
| 配置模型（v2） | ✅ 完整 | `translate/project_map.py`：`modules/targets/memory/dtypes`，校验 M1–M5、T1–T3、MM1–MM5 |
| 内存段 | ✅ 有 | `memory.pool_bytes` / `alignment` / `max_array_bytes` / `arrays` |
| 静态池**能力** | ✅ 有 | `m2c build --static-pool N --pool-align A` 实测**改变产物**（头文件 diff 非空） |
| 配置 → 生成器 | ❌ **缺** | `m2c build` 没有 `--config`；仓库里没有任何代码把 `pool_bytes` 传给 `--static-pool` |
| 配置 → 清单 | ⚠️ 部分 | `project_map.py` 能产 `manifest.h`（`M2C_MEM_POOL_BYTES`），但那是**旁路产物**，与 `m2c build` 的产物无因果关系 |

**这就是 P1 的"唯一生效点"要求的真实缺口**：今天改 `memory.pool_bytes`
只影响 `manifest.h`，**不影响** `gen.c` / 平台宏 —— 所以"改一处配置 → 只有对应行变化"
这条判据目前**不可能通过**。

**最小实现**（下一步，一轮可完成）：新增 `tools/project_build.py`：
读配置（唯一 reader）→ 跑 `mir.py` → 跑 `m2c build --static-pool/--pool-align`，
支持 `--dry-run` 打印两条命令；判据：改 `pool_bytes` 后生成物**确实**变化，
且 `grep` 证明只有 `project_build.py` 读这份配置。
