# 设计（增补）：MATLAB 官方怎么解，本项目怎么改（R689）

> 承接 `docs/DESIGN_SEMANTIC_CORE.md`。本文只做设计。

---

## 一、先问：MathWorks 遇到"翻译不完全"怎么办？

MATLAB 官方有 **四条完全不同的路**，而它们各自解决的是不同的问题——

| 产品 | 做法 | 本质 |
|---|---|---|
| **MATLAB Coder** | 先建**带类型的 IR**，再做代码生成 | 真翻译 |
| **MATLAB Compiler SDK** | 不翻译，**打包一个解释器**一起发 | 不翻译 |
| **Simulink Coder** | 以**块级类型信号**为边界 | 翻译"已定型的模型" |
| **HDL Coder** | 同 Coder + 硬件约束 | 翻译 + 硬件子集 |

我们要对标的是 **MATLAB Coder**。它的四个机制值得逐条抄。

---

## 二、MATLAB Coder 的四个关键机制（逐条对照本项目）

### 机制 1：**类型推断 + 只在歧义处要声明**

Coder 不要求你给每个变量标类型。它做**类型传播**：从 `x = 1:5` 推出 `1×5 double`，
从 `sum(x)` 推出标量；**只有推不出来时**才报错，并要求用 `assert` / `coder.typeof` 约束。

| 本项目 | 差距 |
|---|---|
| 每个数组都要 `% @m2c shape x 5` | **全声明**，缺一个就 `unmapped` |
| 没有推断 | `y = x` / `ones(m,n)` 的形状全靠人填 |

**这是最大的差距**：我们的"映射不完全"里，有相当一部分其实是**"形状没声明"**，
而形状有 80% 可以从上下文推出来（`x(1)` 说明 `x` 至少 1 维；`[a;b]` 说明列数相同）。

### 机制 2：**能力按签名登记，不按函数名**

Coder 的支持列表是 `sum` 支持 `sum(A)`、`sum(A,dim)`，但**不支持** `sum(A,'omitnan')`。
即"支持程度"是**签名级**的，可以部分支持。

| 本项目 | 差距 |
|---|---|
| 表里 `OP-SUM` 只有一条 `sample: y = sum(x);` | 无法表达"支持 1 参、不支持 2 参" |
| `sum(x,2)` 直接落 `unmapped`（类别还叫 `call2`） | 归因丢失 |

### 机制 3：**入口函数**概念 —— 只要求入口完全可定型

Coder 编译的是**入口函数**，被调函数只需"可达且可解析"，不要求每个都独立可编译。

| 本项目 | 差距 |
|---|---|
| 一个文件里任一函数有 `reject`，整份产物就变桩 | 粒度太粗 |
| 三个真实库里 48% 因签名被拒 | 其中不少是"辅助函数"，本不该被当入口 |

### 机制 4：**Extrinsic 逃生口** —— 不可翻译的函数回退给宿主

`coder.extrinsic('fplot')` 让该调用在 MEX 模式下**回调 MATLAB**，而不是编译失败。

**但要注意一个硬约束**：`coder.extrinsic` **只适用于 MEX / 非独立目标**；
生成**独立 C/C++** 时不允许（没有 MATLAB 可回退）。

| 本项目 | 差距 |
|---|---|
| 不支持 → 生成 `return MLC_UNIMPLEMENTED` | 整条路径死掉，无法"部分可用" |
| 没有"宿主回调"的概念 | 无法表达"这里交给外部实现，其余照常生成" |

**我们的等价物**（诚实版，因为要出独立 C）：
把不可翻译的调用生成成**契约桩** —— 一个显式声明、由用户实现的 C 函数：

```c
/* 由用户提供：y = fplot(x)，语义见 docs/contracts/fplot.md */
mlc_status ext_fplot(mlc_array x, mlc_array *y);
```

好处很具体：**函数其余部分仍可编译运行**，未实现处调用即返回 `MLC_ERR` 而不是整份变桩。

## 三、据此修订的框架（v2）

在 `DESIGN_SEMANTIC_CORE` 的三件事（登记表 / kind / 归因）之上，加 **四件**：

```
                    ┌── 能力登记表（按**签名**登记，不按名字）──┐
                    │  mean(vector)->scalar      : 支持          │
                    │  mean(vector,dim)->matrix  : 支持          │
                    │  mean(matrix,'omitnan')    : **不支持**    │
                    └────────────┬──────────────────────────────┘
                                 │
   MATLAB ──①解析──► Core IR ──②类型推断──► 定型 IR ──③发射──► C
                        │            │                        │
                        │            └─ 推不出 → 请求声明（不是直接失败）
                        └─ 解析不了 → 契约桩（extrinsic 等价物）
```

| 新增 | 内容 | 抄自 |
|---|---|---|
| **A. 局部类型推断** | kind 格（scalar/vector/matrix/record/cell）+ 沿语句传播；只在**歧义点**要求声明 | 机制 1 |
| **B. 签名级登记** | 表里每个算子登记**多条签名**，各自标 supported / unsupported + 理由 | 机制 2 |
| **C. 入口函数** | 只有入口函数要求"完全可定型"；被调函数允许是桩 | 机制 3 |
| **D. 契约桩** | 不可翻译的调用 → 生成 `ext_<name>` 声明 + 文档 + 运行期 `MLC_ERR`，**其余照常** | 机制 4（改造版） |

### D 为什么比"整份变桩"好

今天的做法是一个未映射语句 → 整个函数 `return MLC_UNIMPLEMENTED`。
结果是"能生成的函数"很少（YALMIP 26 个）。而契约桩让：

- 生成物**能编译、能跑**，只在走到那一步时返回明确错误；
- 用户看到的是 `ext_plot_model not implemented`，**知道该补哪一个**；
- 上层逻辑（数据搬运、循环、参数校验）全部可用。

这是"部分正确"优于"整体失败"的典型。

## 四、不能抄的部分（诚实边界）

| MATLAB Coder 有 | 本项目不做 | 原因 |
|---|---|---|
| 完整类型推导链（含函数间传播） | ❌ | 需要全程序分析，工程量 10 倍于本项目 |
| 定点/单精度类型系统 | ❌ | 已有 q15 目标，但不做类型推导 |
| 半自动 `coder.varsize` 上界推断 | ❌ | 运行时维度已有 `*_alloc` 路径覆盖 |
| 完整函数支持库（数千函数） | ❌ | 只能按签名逐步登记 |
| Extrinsic 回调 MATLAB | ❌ 改为**契约桩** | 独立 C 目标没有 MATLAB 可回退 |

**一句话**：抄"结构"，不抄"规模"。

## 五、修订后的路线（替换原 S1–S5）

| 阶段 | 内容 | 轮次 | 判据（量化） |
|---|---|---|---|
| **S1 登记表归位** | 正则/映射全部从表派生；表支持**多签名**与 `supported/unsupported` | 2 | 三段对拍仍 58/58；新增算子只改 1 个文件（写成判据） |
| **S2 归因升级** | `unmapped` 记录"期望签名 vs 实际实参 kind" | 1 | 抽查 20 条诊断，全部能说出期望/实际 |
| **S3 局部类型推断** | 从 `x(1)`、`[a;b]`、`sum(x)` 等推出 shape；**没有推断时才要求声明** | 2 | 语料里**删掉一半** `% @m2c shape` 注解后仍 58/58 |
| **S4 契约桩** | 不可翻译调用 → `ext_*` 声明 + 运行期 `MLC_ERR`，其余照常 | 1~2 | 18 个"结构体数组"函数从"整份变桩"变成"能生成、局部失败" |
| **S5 重测** | 对 115+80 个函数批量声明 + 桩化，量翻转 | 1 | **翻转 ≥ 40**（当前 26） |
| **S6 收口** | 边界写进拒绝理由；发版 | 1 | 拒绝理由 100% 可行动 |

**总计 8~9 轮**（比原计划多 2 轮，因为加了推断与契约桩）。

## 六、一个立刻可验证的小实验（下轮第一件事）

不用改架构就能验证 S3 的可行性：

1. 从语料里挑 10 个函数，**删掉它们全部的 `% @m2c shape` 注解**；
2. 加上最小推断（只做两条：`y = x(1)` ⇒ `x` 至少 1 维；`y = [a;b]` ⇒ 列数相同）；
3. 看能恢复几个。

若 10 个里能恢复 ≥5 个 → S3 值得做；若 ≤2 → 说明形状推断在本项目语境下不划算，
应把轮次让给 S4（契约桩）。

**这个实验的价值**：它用 1 轮验证一个 2 轮的假设，且无论结果如何都能写进设计文档。

## 七、结论

**你问的"能不能用通用语义框架解决" —— 能，但框架的重心不是"多支持几个函数"，而是三件事：**

1. **能力按签名登记**（知道"支持到什么程度"）；
2. **类型局部推断**（把"没声明"从失败变成可推）；
3. **契约桩**（把"不支持"从整体失败变成局部失败）。

第 3 条是最被低估的：它不提升"能转的函数数"，但它让**已经能转的部分真正可用**。

---

## 八、§6 实验结论：**S3（类型推断）被否决**

按 §6 的方案做了实验：把语料里全部 `% @m2c shape` 注解删掉，重扫，看还有几个能转。

```
有注解：可转 58 个函数
删注解：可转  9 个函数      ← 只有 15% 能脱离声明
删注解后失去可转：49 个
```

**结论：形状声明是承重的，不是可推导的。** 局部推断（只做
`x(1) ⇒ 至少 1 维`、`[a;b] ⇒ 列数相同` 这两条）不可能补回 84% 的缺口 ——
因为真实缺的是**具体维度值**（`[1 4]` vs `[4 1]`），而它来自作者意图，不来自语法。

⇒ **S3 不做**（原计划 2 轮），把轮次转给：

| 调整 | 原计划 | 修正后 |
|---|---|---|
| S3 局部类型推断 | 2 轮 | **0 轮（否决）** |
| S4 契约桩 | 1~2 轮 | **3 轮（提为首要）** |
| S5 批量声明 + 重测 | 1 轮 | 1 轮 |

修订后总计 **7 轮**。

**为什么契约桩优先级更高**：它不提升"能转的函数数"，但它把
"一个未映射语句 → 整份变桩"改成"整份可用、局部报错"。
按 R686 的普查，YALMIP 里 80 个函数"只差一条"——契约桩能立刻让这 80 个**产出可用的 C**，
哪怕那一处返回 `MLC_ERR`。

**这与 MATLAB Coder 的取舍一致**：Coder 用 `coder.extrinsic` 换"部分可用"，
我们用契约桩换同样的东西（因为独立 C 没有 MATLAB 可回退）。
