## §1 白帽：事实与读数

### §1.1 靶子（R63 §8 C13-9，优先级「最高」）

R63 收尾时量出一件怪事：同一个 `matlabc.py`，`--help` 的字节数**不是一个数**。

| 量法 | 读数 |
| --- | --- |
| Python **3.10.10** | **50481**（559 行） |
| Python **3.13.12** | **50451**（558 行）＝ `HELP_BYTES_SNAPSHOT` |
| 3.10 ＋ `COLUMNS=200` | **45827** |

而旧容差是 `max(30% × 快照, 512)` —— 对 matlabc.py 就是 **15135 B**。
⇒ **一个自称精确的棘轮，分辨率比它记录的数字粗 200 倍。**

### §1.2 修复前：旧棘轮逐入口的分辨率

| 入口 | 快照 | 旧允许带 | 最小可检漂移 |
| --- | --- | --- | --- |
| `matlabc.py` | 50451 | **15135** | **15136** |
| `matlabc_flow.py` | 2075 | 622 | 623 |
| `matlabc_ask.py` | 919 | 512（512 B 下限） | 513 |
| `gui.py` | 2651 | 795 | 796 |

**R64 之后**：允许带 `HELP_DRIFT_BYTES = 64`，最小可检漂移 **65 B**（全入口一致）。
⇒ 旗舰入口 **15136 → 65 B（约 233 倍）**；再叠一条**容差 0** 的精确臂（**1 字节**）。

### §1.3 根因：两条**互相独立**的方差轴

#### 轴 1 —— 解释器：恒定 −30 B，**不是折行**

| `matlabc.py --help` | 3.10 | 3.13 | 差 |
| --- | --- | --- | --- |
| COLUMNS 未设 | 50481 | 50451 | **−30** |
| 200 | 45827 | 45797 | **−30** |
| 1000 | 45082 | 45052 | **−30** |
| 4000 | 45025 | 44995 | **−30** |
| 10000 | 45025 | 44995 | **−30** |

差值**在所有宽度下恒定** ⇒ 与折行无关。逐行比下去，全部差异就是**一行**：

```
3.10:   -o OUTPUT, --output OUTPUT      ← 多出这一行（恰好 30 字节）
                输出 Markdown 报告文件路径
3.13:   -o, --output OUTPUT    输出 Markdown 报告文件路径
```

后面 490 行「不同」只是这一行造成的**行号位移**。
这是 argparse 的行为变更：**3.10 会把 metavar 同时印在短选项上，3.13 起不再印。**

规范化（裁行尾空白 / 去掉尾部空行 / 折叠连续空行）**都去不掉它**（残留 −29 B）——
因为那是**布局**差，不是空白差。这一条决定了 R64 的做法：不能靠「清洗空白」，
要靠**折叠布局 + 只留内容**（见 §3.3）。

#### 轴 2 —— 环境：`COLUMNS` 从**父进程漏进子进程**

`_run_safe_example` 起子进程时**不设 `env=`** ⇒ 完整继承调用方环境。
而 `argparse` 的宽度走 `shutil.get_terminal_size()`，它**优先读 `COLUMNS` 环境变量**
（与 stdout 是不是 tty **无关**）。实测受影响 3/5 个入口：

| 入口 | `COLUMNS` 200 − 未设 |
| --- | --- |
| `matlabc.py` | **−4654** |
| `matlabc_flow.py` | −144 |
| `matlabc_ask.py` | −40 |
| `gui.py` / `matlabc_mcp.py` | 0（文本短，没到折行点） |

⇒ **从 200 列的终端跑这道门，读数与 80 列的不是同一个。** 这是一条真 bug。

### §1.4 顺手量出的第三件事：旧带把**环境泄漏也一起吞了**

把「漂移量」逐档喂进两套判据（快照 50451）：

| 漂移 (B) | 新读数 | 旧带 ±15135 | 新带 ±64 |
| --- | --- | --- | --- |
| 0 | 50451 | 放行 | 放行 |
| 30 | 50481 | 放行 | 放行 |
| **64** | 50515 | 放行 | **放行**（带边界） |
| **65** | 50516 | 放行 | **红** |
| 250 | 50701 | 放行 | **红** |
| 400 | 50851 | 放行 | **红** |
| **−4654** | **45797** | **放行** | **红** |

最后一行是关键：`−4654` **正是** `COLUMNS=200` 造成的那个漂移。
⇒ 旧棘轮对「从别的宽度跑」这件事**不是「抓住但容忍」，而是根本没有分辨率**。
R64 把带收紧到 64 B 之后，「钉死口径」从**装饰**变成**承重**：
一旦有人把钉死去掉，这道门会当场变红（`tests` 里有一条现场量的反事实判据守着这一点）。

## §2 黑帽：这一版**不解决**什么

1. **规范形看不见布局**：缩进、折行位置改了它不知道。这是**管辖范围**，不是遗漏；
   布局由臂 ①② 兜（§3.3 的诚实声明与 `--selftest` 的「折行位置不同 ⇒ 规范形相同」样本）。
2. **规范形依赖一条窄规则**（去掉 3.10 的 metavar 重复）。若某个解释器产生**另一种**
   渲染差异，规范形会变 ⇒ **变红并点名**，需要人判断后更新快照。
   这是**响铃**不是静默，但它确实要求维护者认得这个签名。
3. **64 B 带对辅助入口变紧了**：`matlabc_ask.py` 快照 919 B，64 B ≈ **7%**。
   一次合法的帮助增删也会红。这是**故意的**（合法增长应在同一提交里更新快照），
   但它是行为变更，写在这里免得下一轮当成回归。
4. **钉死 80 列改变了绝对界的语义**：从「调用方的宽度」变成「80 列」。
   两臂都更可复现，但 64 KiB 那个上界现在是对 80 列而言的。
5. **缓存键变了**：旧键 `script + "::--help"` 不区分测量口径；新键带 `@C<列数>`。
   代价是每个入口多跑一次 `--help`（臂 ③）；收获是**堵掉一个隐患** ——
   若将来 R4 也在同一份缓存里跑 `--help`，两条臂会互相污染读数。
6. **它仍然是「尺寸」棘轮**：等长改写看不见（例如 R63 的 `14 道` → `15 道`，字节中性）。
   这是所有体积棘轮的固有边界，**不是本轮引入**，也不声称已解决。

## §3 落地物（全部真实现，无占位符）

### §3.1 钉死测量口径

`_run_safe_example(root, script, argv, env_extra=None)` —— 新增第四个参数，
在**继承来的**环境之上追加/覆盖若干变量。R5 的两条臂各自钉死：

* 臂 ①②：`COLUMNS = 80`（终端里真读得到的口径）；
* 臂 ③：`COLUMNS = 10000`（宽到不再折行）。

### §3.2 容差：百分比带 → 绝对字节带

`HELP_DRIFT_MAX = 0.30` + `HELP_DRIFT_FLOOR = 512` **删除**，换成
`HELP_DRIFT_BYTES = 64`。理由写在源码注释里，不是「调出来的数」：

> 实测**唯一**的跨解释器差是 matlabc.py 的 30 B；64 = 2 倍余量。
> 分辨率因此从 15135 B 提到 64 B。

### §3.3 第三臂：规范形逐字节相等（分辨率 1 字节）

新增纯函数 `_canon_help(raw)`，两步：

1. 去掉 argparse 3.10 的 metavar 重复（`_CANON_DEDUP_RE`，用反向引用要求两个
   metavar **逐字相同**，规则刻意窄，免得误伤正文）；
2. 把**所有**空白串（含 CR/LF）折叠成一个空格 —— 这一条同时抹掉「折行」与
   「帮助是换行到下一行、还是接在同一行」两种**布局**差。

实测 **2 个解释器 × 3 个宽度 = 6 个读数 → 1 种规范形**（4 个入口 + stdio server）：

| 入口 | 6 读数的规范形种类 | 规范形字节（新快照） |
| --- | --- | --- |
| `matlabc.py` | **1**（全等） | **42053** |
| `matlabc_flow.py` | **1** | 1701 |
| `matlabc_ask.py` | **1** | 756 |
| `matlabc_mcp.py` | **1** | 0 |
| `gui.py` | **1** | 2290 |

于是 `_r5c_verdict` 的容差写成 **0**：规范形与解释器和宽度**都无关**，
再有的差异只可能来自**内容**。

> 诚实声明（写进函数 docstring）：规范形**看不见布局**；
> 本条只守内容，布局由臂 ①② 兜。

### §3.4 缓存键带测量口径

`script::--help` → `script::--help@C80` / `script::--help@C10000`。
两条臂的读数不再可能互相复用。

### §3.5 文档与可见性

* 门的成功行现在**打印自己的分辨率**：
  `帮助体积三臂（绝对界 / 漂移带 ±64 B / 规范形容差 0）在钉死 80 / 10000 列下实测`；
* 门 docstring 的 R5 段重写 + 新增 R5c 段（含诚实声明）；
* 两侧 README 的 `check_help_contract.py` 表行同改（**保留 `B0–B5`**，P5 靠它）；
* `CONTRIBUTING.md` 新增一节（含三条根因与修法）。

## §7 盲区（诚实列表）

1. **规范形看不见布局**（§2 第 1 条）—— 已写进函数 docstring 与本文档。

   这条相等由 `tests` 断言（不是由门自己断言）。见 §8 C14-8。

7. **`_run_safe_example` 的其他调用点不钉口径**（R4 的示例仍继承完整环境）——

## §9 明确拒绝做的事（避免下一轮走回头路）

1. **不为了「让读数好看」把 `COLUMNS` 钉到 200 或 10000 去对齐旧快照**：
   80 列是「终端里真读得到」的口径，快照也是按它记的。改口径要连快照一起
   走一次显式批准，而不是偷偷挑一个能过的数。
2. **不放宽 `HELP_DRIFT_BYTES`**：它的值有实测依据（30 B → 2 倍余量）。
   合法增长应在同一提交里更新快照 —— 那是一次可评审的批准动作。
3. **不为了让规范形「更稳」而把它做成哈希**：哈希能比相等，但失败时说不出
   「差了几字节、差在哪」。字节数至少能让维护者一眼看到量级。
4. **不用「规范化」去抹掉** 3.10 那一行以外的**任何**东西：规则越宽，
   内容被抹掉的风险越大。现在的规则要求两个 metavar **逐字相同**，且必须在行首
   两个空格之后。
5. **不把 `--help` 的渲染改成「版本稳定」的产品行为**（例如给 `ArgumentParser`
   换 formatter）：那会改变**用户可见**的输出，而本轮的目标是修**测量**，不是改产品。
6. **不动 `VERSION`、不动 `flow/diagrams`、不引新依赖、不动行尾策略**。
