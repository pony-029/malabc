# R85 复盘 — 把「内核分析流程」从口头知识搬成有对手方的登记表

> 判据来源：白帽**以实测为准**（逐脚本读源码 + 门当场开火 4 次 + 远端全新克隆复核）。
> 本轮范围：**只加判据族 W6 + 改登记表 + 级联五处**，产品侧（`matlabc.py` 的分析逻辑）**一行未动**。

## 0. 一句话

用户问「内核代码的分析流程在哪里」—— 白帽实测的答案是：**流程完整，但只活在 8 个脚本的
docstring 里**，散在两棵仓外树，没有任何一处能回答「有哪几站、该跑哪一代」；代价是可实测的
（盘上同时躺着三代驱动，其中一代再跑就**吃掉对照基线**）。本轮把它搬进 `docs/KERNEL_RUN.md`
的「分析流程登记」段，并用第 19 道门的**判据族 W6（W1–W5 → W1–W6）**把「站表形状 / 恰一个
current 驱动 / 产物链拓扑 / 仓内落点存在」钉成机器可裁决的不变量。

## 2. 红帽 —— 直觉

* 这一轮**没有产品侧的进展**。门数没涨（19），`matlabc.py` 一行未动。纯工程量堆在
  「让知识可被机器裁决」上 —— 直觉上**回报不直观**，但 §1.2 第 3 条说明它抓到的
  恰恰是「分类错误」这类**没有任何功能测试会发现的缺陷**：`chunks` 被误标成主驱动，
  分析结果照样出、测试照样绿，只有站表读出来是错的。
* 对「门报标记出现 2 次」的第一反应是「这也算 bug？」—— 这个反应本身是要记下来的：
  **判据里最像洁癖的那一条，往往在拦最隐蔽的错**（R83 定论：口径类缺陷比功能类危险）。
* 隐约不安：站表是**手写元数据**，它描述的是一堆**仓外脚本**。手写的元数据会漂移，
  而漂移的对手方（`gen_kernel_run_doc.py --check`）还没进门禁。

## 3. 黑帽 —— 风险

| # | 风险 | 最坏情况 | 现有对手方 | 缺什么 |
|---|---|---|---|---|
| **B1** | **「仓外只计数不裁决」被滥用** | 以后有人把一条**真该裁决**的存在性判据也归到「仓外」名下，门从此对那块失明 | W6e 只对**仓内落点**（4 个）裁决，且 `info["outside_repo"]` **把仓外条数打在读数里**（13 站里 12 个是仓外 —— 数字可见） | 没有一条判据说「仓外比例不许再涨」 |
| **B2** | **站表靠人手维护 ⇒ 漂移** | 新增一个分析器却忘了登记 ⇒ 门仍绿（它只检查表**内部**自洽），而「当前驱动是哪个」变成**两个**答案写在两处 | W6b 恰好一个 current 分析器（能抓「表里有两个」） | 抓不到「**表外**还有一个没登记的」 —— 这需要扫盘，而扫盘在仓外 |
| **B3** | **`role` / `status` 是我一个人定的闭集** | 闭集太小 ⇒ 未来的合法角色塞不进去 ⇒ 有人为了让门过而**错分类**（正是第 3 次开火的原因） | 闭集在门里显式列出；`probe` 是**这一轮才补的** | 没有任何机制保证「闭集是完备的」 |
| **B4** | **`why` 字段是自由文本** | 有人写 `why=xxx` 应付过去 | 只在「非 current 或 probe」时要求**非空** | 不检查 `why` 的内容质量（**刻意**：内容质量没法机器裁决，硬做会造假绿） |
| **B5** | **登记表与生成器不同步** | 直接手改 `docs/KERNEL_RUN.md` 而不改生成器 ⇒ 下次生成覆盖掉手改 | W1 形状 + W6 判据都在门上 | `--check` 差集：**这一轮没接** |

## 4. 黄帽 —— 价值

* **把「该跑哪一代」从人的记忆变成机器的不变量。** 之前 13 站的顺序与代际活在 8 份
  docstring 里；现在 13 站在册、`role/status` 闭集化、产物链拓扑可重算。B2 里那个
  「R81 再跑一次就吃掉基线」的坑，**现在至少写在 `why` 里**（`why=OUT 写死 r81/ 且按
  label 合并 ⇒ 再跑会就地覆盖对照基线（基线是对照的另一半）`）。
* **判据族从 5 条涨到 6 条，门数不变。** 这是「缺口为 0 时加闸 = churn」的直接应用 ——
  本轮**不给门数棘轮加数**，而是给已有的一道门**提分辨率**。既有的 5 处级联点
  （`MIN_GUARDS` 不用动）因此不膨胀。
* **一个量一份实现**：`parse_block` 改造成读数块与流程块**共用同一个解析器**
  （`open_mark`/`close_mark`/`tag` 参数化）。两块各写一份解析器是**下一条 B4/B5 级
  漂移**的种子（§4x-5）。
* **`W6e` 的边界是主动划的**：存在性只对仓内 4 个落点裁决。如果把 12 个仓外路径也
  纳入裁决，就会造出一道**只在开发机上绿**的门（新克隆没有 `_kernel/`）——
  正是 **L59** 要防的。

## 6. 蓝帽 —— 综合结论

1. **「流程在哪里」这个问题已经被接住，但只接住了一半。** 站表在册、代际钉住、
   仓内落点有对手方（§1.1 / §1.2）；**站表本身的陈旧性没有对手方**（§3 B5）。
2. **本轮最大的收获不是 W6，而是第 2、3、4 次开火。** 三次都是**功能测试永远抓不到**
   的缺陷：文档里的多余字面量、站表的错误分类、级联点的遗漏。这坐实了 R82/R83 的定论
   「口径类缺陷比功能类缺陷危险」。
3. **边界必须显式写出来，否则会被下一次滥用。** `W6e` 的「仓外只计数不裁决」这一条，
   现在写在门的 Readme 描述里、写在 `info` 读数里，但**没有写成一条判据**（§3 B1）。
4. **产品侧仍然一行未动（R82 起连续 5 轮）。** 这是 Phase 0 的**有意设计**，但
   Phase A 的三条 blocked 轮次（A1/A2/A3）从第 3 轮起就挂着 —— 轮到问了：
   **Phase 0 的地基还要铺几层才够？**（§7 的 R86 建议把它摆到台面上。）

## 7. 下一步（R86，按价值排序）

1. **给 `unknown` 下降配对手方**（R84 起挂了 2 轮，仍是最高价值）
   —— 挪动 `unknown` 后必须**同时**断言 `join` 上升 Δ **且** `async` 不变。
   只断言「unknown 下降」是**可以靠分类错误刷出来的**（R83 定论：把 `await` 从 unknown
   挪进 join 就能让 unknown 掉，但那不是收敛证据）。这条是**唯一一条能同时防住
   「假收敛」和「口径漂移」的判据**。
2. **`js/await` 登记为 `join`** —— `await` 已在 `py` 表、`js` 表**缺它**；`js` 里的
   2,039 条（`unknown` 的 78.2%）全在漏。改 3 处：`concurrency.py` 的 js 表 +
   `EXPECTED_OUTCOMES["js"]` + README 的「20 条映射」→ **21**。
   （有 1 号判据做对手方 ⇒ 这一条改完必须**看到 join 上升且 async 不变**才接受。）
3. **第三条并列口径 `segment`** —— 按 `_` 切段、排除 dunder。理由：匹配器看不见
   `_` 包裹的小写词干（`mutex_lock` / `pthread_mutex_lock`），实测同步桶只有 27 条
   (1.0%)；它与 `__future__`（要排除）**形状同类**，纯形状分不开 ⇒ 只能**并列报**。
4. **回归清单接进门禁** —— `_r82\gen_unknown_registry.py --check` 陈旧即红
   （R85 的 §5 G1 是同一件事的另一半：登记表类文档都该有 `--check` 对手方）。
5. **出处清单化** —— 本轮查实内核 C 臂只依赖 `matlabc.py`，但这句话**本身没有门看着**
   （§3 B2）。做法：把「本轮这些读数是由哪几个文件算出来的」写成**清单**并逐个钉 sha256。
6. **`docs\UNKNOWN_SITES.md` 并列内核两档分母** —— 与 `docs\KERNEL_RUN.md` 的三档一致。
7. **路线图登记**：把 1/2/3 写进 `EVOLVE_ROADMAP_360.md` 的 `ROUNDS:PLAN v1` 块。
