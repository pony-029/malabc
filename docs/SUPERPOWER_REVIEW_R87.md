> 读数口径：**换行符数**；分母一律**指名子树**；数字来自定稿之后的回归，不引历史值。

## 1. 白帽 —— 事实与读数

### 1.1 缺陷族的三个通道（全部由隔离探针跑出来，不是读代码读出来的）

| 通道 | 现场 | 内核实测 | 后果 |
|---|---|---|---|
| **D1 定义侧** | `typedef struct __attribute__((packed, aligned(4))) {` | **7 处 / 2 文件**（`smu_v13_0_6` 4 + `smu_v13_0_12` 3） | 产出名叫 `__attribute__` 的**假函数**；那两个文件的函数表 **100% 为假** |
| **D2 调用侧·属性头** | `__attribute__((weak,unused,section(…)))` 独占一行，夹在声明与定义之间 | `tools/include/nolibc/string.h` 的 21 个函数**每个**一条 | 定义没丢，但 `line` 落在属性行；`__attribute__(` 被当调用 ⇒ **假边** |
| **D3 调用侧·组内参数** | `((packed, aligned(4)))` 里的 `aligned(`（前一个字符是「逗号 + 空格」） | 内核 7 条 | 假调用 ⇒ 进 `unresolved`，**直接抬高对外读数** |

⚠ 一条**反直觉**的对照，也是探针跑出来的：`((aligned(4)))` **不**泄漏 ——
`aligned` 前一个字符是 `(`，被既有的 `prev in ("*","&","(",")")` 规则挡掉。
换句话说「属性参数泄漏」不是一条规则，而是**依赖前一个字符**的。这解释了为什么
只按名字排除 `__attribute__` 不够，必须**整组屏蔽**。

### 1.2 我第一次对根因的判断是错的

我以为缺陷只有一种形态（`typedef struct __attribute__(…)`）。探针的现场输出显示
D2 是**另一个机制**：定义没丢、`line` 错位。**是探针纠正了我，不是我再读一遍代码。**

### 1.3 修复自己引入的第三个缺陷（R87g）—— 本轮最值钱的一条

`_is_type_decl()` 第一版扫的是 `range(decl_start, i)` **整段**，而 `decl_start` 只在
`;` / `{` / `}` / 预处理行处重置。内核里成串的**无分号宏调用**把它长期钉在远处：

```
DEFINE_PROCESS_TYPE(typedef)            # 396 行 —— 这个 typedef 是【宏参数】
…
static void process_subrange_type(…     # 398 行 —— 真函数，被区间里的 typedef 吃掉
```
```
BTF_ID_LIST_GLOBAL(test_list_global, 1) # 47 行 —— 无分号
BTF_ID(typedef, S)                       # 49 行 —— typedef 在括号【内】
…
static int
__resolve_symbol(struct btf *btf, …)     # 66 行 —— 真函数，被吃掉
```

判据是**括号深度 0**：类型定义的 `typedef` 在属性组的 `(` **之前**，宏实参的
`typedef` 在 `(` **之后**。

`_r87/explain_delta.py`（同一 token 流跑两种行为、逐文件对照）给出的收窄过程：

| | 丢掉的假定义 | 明细 |
|---|---|---|
| 第一版修复 | **11** | `__attribute__` × 7 + `CAT2` × 1 + `CONCATENATE` × 1 + **误伤 2 个真函数** |
| 收窄后（定稿） | **9** | `__attribute__` × 7 + `CAT2` / `CONCATENATE` × 2（`enum <宏调用>(...)`，**该丢**） |

丢掉的调用点 **710 条**，全部属属性族：`__attribute__` 691 / `format` 12 / `aligned` 7
—— **没有一条真调用被误伤**。

### 1.3b 修复暴露出的**既有**缺陷：`decl_start` 被无分号宏调用钉住（R87i，本轮只登记不修）

`_r87/probe_roots.py` 对两个内核真文件跑公开 CLI，读到的记录：

| 函数 | 记录里的 `line` | **真定义行** | `ret`（返回类型） | `calls` |
|---|---|---|---|---|
| `process_subrange_type` | **385** | 398 | `DEFINE_PROCESS_TYPE(atomic) DEFINE_PROCESS_TYPE(const) …` | 15 条，其中 **11 条是 `DEFINE_PROCESS_TYPE`** |
| `__resolve_symbol` | **47** | 66 | `BTF_ID_LIST_GLOBAL(test_list_global, 1) BTF_ID(typedef, S) …` | 21 条，其中 14 条是 `BTF_ID*` |

⇒ **同一个根因（`decl_start` 被无分号宏调用钉住）有三个症状**：
`typedef` 判定误判（R87g，**已修**）、`line` 错位、`ret` 与 `calls` 的**归属范围被撑大**
（后两个是**既有**缺陷 —— 本轮修复只是把它们从暗处推到了明处，与 R86-3 是同一个模式）。

记为 **R87i**，下一轮做。**不在本轮顺手改**的理由：它需要先把「函数归属应当从函数体的
`{` 起算」设计成**判据**（而不是改一行），且改它会再次改变全部读数 —— 顺手改一行，
下一次内核重跑就会多出一组**没有出口**的 delta。

### 1.5 第 19 道门的 W5 出口（R87h）

W5 原本断言「与 R81 逐位全等」。R87 起分析逻辑**真的变了**，而门自己的措辞早就
留了出口：「或分析逻辑真的变了，那就必须写出原因」。

登记表因此新增**第三个块**「与 R81 的已声明变化」（复用 `parse_block`，`键 | 值`）：
数字由生成器**现算**，原因由人写，**没写就是空串、照样落盘 ⇒ 门红**。
W5 改为「**计数相等 ⇔ 未声明变化**」。

## 3. 黑帽 —— 风险

1. **W5 出口 = 通行证？** 如果只做「声明了就放行」，任何差值都能被一张表洗白。
   对策：三向对手方 —— 未登记 ⇒ 红；**相等却仍被登记 ⇒ 红（陈旧登记）**；
   幽灵登记 / 数字与实测不符 / 原因栏为空 ⇒ 红。
   「陈旧登记」这一向是关键：它让这张表**不能只增不减**。
2. **生成器替门原谅差异？** 对策：生成器把**没能解释**的差值也写进块（原因留空），
   门来裁决。**生成器不隐瞒，门来裁决。**
3. **反复出现同一类错**：R86-3 是「修呈现缺口让旧缺陷浮上来」，本轮反过来 ——
   **修复本身引入了新缺陷**。两次的共同点：**缺陷都藏在「我以为已经想全了」的地方**。
4. **`_mask_c_attrs` 是行内机制**：属性组跨行时组身那行不含 `__attribute__` 头 ⇒
   不保证屏蔽。这条**已写进文档与判据**（不静默）。
5. **噪声与泄漏混为一谈的风险**：夹具新增宏调用后，`DPT` / `BTF_ID` 必然落进
   `unresolved`（宏未展开，与属性无关）。若简单塞进期望，就会掩盖两类差异的区别。
   对策：**分开登记** + 「噪声不多不少」+ 两本账**自维持**对账。

## 4. 黄帽 —— 价值

- 内核读数里有 **129 万** `unresolved`；D3 这类假调用是**读数污染**，
  它抬高的是**对外可见的数字**。修掉它，读数的**可信度**整体上移。
- `_is_type_decl()` 的「声明前缀」判据是 **C 语法硬约束**（不是启发式），
  所以它可以解释、可以证伪、可以被变异体钉住。
- 「括号深度」这个判据是可**推广**的：任何「区间扫描 + 起点可能被钉住」的地方
  （不只是 `typedef`）都该问一次「这个 token 在括号内还是括号外」。
- 交付产物（`kernel_callgraph.json`）里 `__attribute__` 出现 **0 次**（原 15），
  `aligned` **0 次** —— 用户直接看到的东西不再有假节点。

## 5. 绿帽 —— 想法

1. **把「已知噪声登记」做成范式**：`ATTR_KNOWN_UNRESOLVED_NOISE` 这种做法
   （把「已知的、不是缺陷的」读数显式列出并断言「不多不少」）可以推广到
   其它「已知边界会污染读数」的地方。
2. **`decl_start` 的语义值得再问一次**：它的重置条件是词法层的 `;{}` / pp。
   凡是依赖它的判据都会继承同一个脆弱性。可考虑在 `_scan_c_definitions` 里
   维护一个**括号深度**并把它交给所有前缀判据。
3. **差值解释器可以常驻**：`explain_delta.py` 这次只用来解释一次。把它做成
   「任何一次内核重跑后都能自动跑」的步骤，就能让每一次 delta 都自带解释。
4. **下一步（已排入路线图）**：**符号级身份（definition-site）** —— 见 §7。

## 6. 蓝帽 —— 流程与元

- **门数刻意不变（仍 19）**：缺口为 0 时加闸是 churn，这一轮只提分辨率（R85 定论）。
  改的是**判据族**（F8）与**门的分辨率**（W5 三向），不是闸的数量。
- **「给门加东西先想它会不会反咬」**：W5 出口如果做成「宽恕」，反咬的方式是
  「从此没人看 delta」。三向对手方就是这条纪律的产物。
- **「先问量具错还是对象错」**：门在 `ATTR_C` 加宏调用后报 `unresolved` 多两条
  —— 查清后判定是**量具（期望）没跟上夹具**，不是产品错。这个顺序不能反。
- **命名纪律**：`R87b` 一度同时指「调用侧屏蔽」与「深度收窄」两件事，已改名
  **R87g**。编号复用会让读者把两件事混成一件。

## 7. 下一步（建设性意见）

按价值排序，**首选仍是符号级身份** —— 它是上一轮就提出、这一轮没能做的那条：

> **① 符号级身份（definition-site）**。把调用图节点从「名字」换成「**文件 + 名字**」，
> 至少对同名多定义的那些名字做。理由：`ambiguous` 那一桶在内核里是 **5,153,962 条
> （72.9%）**，而**最大伪环 37,776** 与「同名多定义」是同一件事的两面 —— 环是靠
> 名字合并造出来的。
> 出口判据必须**两向**：同名多定义占比必须**下降**、`ambiguous` 桶只准**变小**、
> 且最大分量掉到 **≤ 三位数**。只断言「环变少了」是可以靠**整类不报**刷出来的。

其余按序：

- **② `js/await` 登记为 `join`**（2,039 条 = 78.2%，`unknown` 里最大单项）。
  必须**同时**断言「`join` 上升 Δ **且** `async` 不变」，否则「把 unknown 挪进别的桶」
  也能让 unknown 掉下来（R83 定论）。
- **③ 把「括号深度」交还给所有前缀判据**（§5.2），从结构上消灭 R87g 那一类脆弱性。
- **④ REA 能力族续接**：#103 里未开始的 ELF 重定位 / GOT / PLT → EVM selectors →
  .NET CIL → JS/Electron 模块图 → HAR。
- **⑤ 文档**：`docs/matlabc_FEATURES.md` §3.15 已记 R87g；下一轮把「三个泄漏通道」
  与「括号深度」搬进 `docs/matlabc_JSON_SCHEMA.md` 的字段口径说明。
