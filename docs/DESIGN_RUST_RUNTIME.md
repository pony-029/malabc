# 设计：用 Rust 写 MATLAB 运行时 —— 该做，但不是取代 C 生成（R690）

> 本文只做设计。架构图见 `.archify/architecture-rust-vm-20261107-232737/candidate.json`
> （渲染产物 `rust-vm-arch.html`，archify 全门通过）。

---

## 一、你的提议拆成两个不同的问题

> "直接写一个 MATLAB 运行时，用 Rust 实现"

这句话里其实有两个诉求，代价相差一个数量级：

| 诉求解法 | 内容 | 解决什么 |
|---|---|---|
| **A. 运行时执行**（解释器/VM） | 把 MIR 直接跑起来，不经 C | 动态特性（cell/struct/varargin）、自证、扩展性 |
| **B. 取代 C 生成** | 只发 Rust runtime + 用户代码数据，不再生成 C | 交付形态变化 |

A 的收益很实在；**B 会打掉现有卖点的根基**：

| 现有卖点 | 若只发 Rust runtime |
|---|---|
| C99、无动态分配、静态内存池 | 需 Rust 工具链进固件；`no_std` + 分配策略要重做 |
| q15 定点 | 要在 VM 里重做数值路径 |
| 可认证（MISRA / 无堆） | 解释器更难论证 |
| 现有 58/58 语料 + 三段对拍 + 相互转换 | 全部作废或需重建 |

---

## 二、推荐：**双轨**

```
MATLAB → MIR ──┬─→ C Emitter → 嵌入式目标（生产路径）
               └─→ Rust VM  → 开发期自证 / 动态特性参照（验证路径）
```

两条轨道**共用同一份 MIR 与同一张能力登记表**，不是两套系统。

### Rust VM 立刻能解决的三件事（都有现成痛点）

1. **不再依赖 Octave 才能得到真值** —— 现在 `roundtrip` 55/55、三段 58/58
   都要 Octave；VM 可以自证。
2. **动态特性由运行时支持** —— `cell`/`struct`/`varargin` 不必"翻译"，
   作为**参照实现**存在，用来验证 C 生成的语义。
3. **新增算子只写一次** —— 现在要改 5~7 处（C/头/表/正则/映射/Rust/文档）。

### 代价（必须明说）

- 解释执行约比生成代码慢 **2~20×**（JIT 才能缩小，工程量大）；
- VM 进固件要 `no_std` + 自己的分配器策略；
- 现有 C 路径的回归基线（58/58）必须保绿 —— VM 不能成为"绕过检查的捷径"。

---

## 三、MCP 接口设计

MCP 只是**薄适配层**，不承载逻辑：

| MCP 工具 | 底层 | 返回 |
|---|---|---|
| `check(path)` | `translate/check.py` | 能否转 / 卡点行号 / 建议注解 |
| `convert(path, out)` | `m2c build` | 产物路径 + 编译结果 |
| `roundtrip(path)` | `translate/roundtrip.py` | 双向数值是否一致 |
| `kpi(dirs)` | `tools/task_kpi.py` | 通过率 + 未通过原因 |

**一条硬约束**：MCP 层**不得**自己判断"能不能转" —— 必须调用 `check`，
否则就出现了第五份"支持定义"（这正是本轮要消灭的东西）。

---

## 四、分阶段（每阶段可停）

| 阶段 | 内容 | 轮次 | 判据 |
|---|---|---|---|
| **V1** | Rust VM 跑通语料：读 MIR，执行 30 个常用算子 | 3~4 | 语料 58/58 的**数值**与 Octave 一致 |
| **V2** | VM 成为 `roundtrip` 的默认 oracle（Octave 变可选） | 1 | 无 Octave 机器上 55/55 仍成立 |
| **V3** | MCP Server（4 个工具）+ 一条"不得自行判断"的判据 | 1~2 | MCP 层无任何 `if 支持` 分支 |
| **V4** | 动态特性参照（cell/struct/varargin 在 VM 里实现） | 2~3 | 用 VM 作参照，验证 C 生成在 20 个函数上等价 |
| **V5（可选）** | `no_std` + 静态分配，VM 可上固件 | 3~5 | 一个真实目标板上跑通 |

**V1 的风险最高**（VM 要把算子语义写对一遍），但它同时是 **V2~V4 的地基**。

---

## 五、为什么不建议先做 B（取代 C）

**因为 B 的收益要等 V5 之后才出现，而 B 的成本立刻发生。**
在 VM 还没证明"语义正确"之前就砍掉 C 路径，等于把唯一的可信产物去掉。

---

## 六、结论

1. **做 Rust VM（A）** —— 它把"自证""动态特性""算子只写一次"三件事一起解决；
2. **不砍 C 生成（B）** —— 保留嵌入式路径，双轨共用 MIR；
3. **MCP 是薄层**，且**禁止**自行判断能力；
4. 第一件事是 **V1**：让 VM 跑通语料并与 Octave 数值一致 —— 这是唯一能证明"值得继续"的证据。
