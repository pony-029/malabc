## 3. 修法（以及**不许**怎么做）

```python
def _rel_of(path, root):          # root **没有默认值**：漏传当场 TypeError
    p = os.path.abspath(path)
    base = os.path.abspath(root)  # 基准是**被分析根**，不是 os.getcwd()
    try:
        r = os.path.relpath(p, base)
    except Exception:
        r = os.path.basename(p)   # 只剩这一条真异常兜底（跨盘符等）
    return r.replace("\\", "/")
```

三条**不许**：

| 不许 | 为什么 |
|---|---|
| 把 basename 换成**绝对路径** | 产物会变成**机器相关**（换台机器字节就变），R89 的绝对路径扫描当场红 |
| 给 `root` 一个**默认值** | 默认值就是一条**静默**的 cwd 回退 —— 缺陷会原地复活而没人知道 |
| 逃逸根时**回退 basename** | 那正是塌陷本身。逃逸时返回**诚实的相对形态**（含 `..`）：仍与 cwd 无关，且**不合并**同名文件 |

四个调用点全部传根：`build_c_model()`（`--lang c` / `--mixed` 两条路）、
`_build_ext_model()`（asm 前端 / 扩展前端）。

**诊断三路独立收敛**（都对上同一个预测，才动手）：

1. `_rel_of` 实现 —— cwd 之外 ⇒ `..` ⇒ basename；
2. `resolve_calls` 对多定义的**扇出** —— 一个调用点命中 N 份定义产 N 条边；
3. `_resolve` 的 **rung 1 按 `rel` 字符串**比较 —— 两个文件塌成同一个 basename ⇒
   「恰一份」不成立 ⇒ 掉进 `K_AMB`。

⇒ 预测（写法以**塌陷态**为准）：塌陷 ⇒ `same_file` **下降**、`ambiguous` **上升**，
而 `edges_total` 一条不变。

实测**半对**：`same_file` 方向**成立**（旧 2,273 < 新 2,370）；
`ambiguous` **方向猜反** —— 塌陷时它反而**降**（19,553 → 17,625），
和 `same_file` 少掉的 97 条**一起**被 `include` 接走（2,034 → 4,059，**多收 2,025**）。
⇒ 这个小夹具与真语料**结论不同**的原因值得记下来：夹具里**没有 include 图**，
歧义无处可去；真语料里塌陷后的 basename 由 **include 闭包**消化掉了。

## 4. 判据 F10l：为什么必须是**直接**判据

**门看不出 `rel` 的形态。** 这是本轮最有价值的一条实测：

| 读数 | 修复前 | 修复后 |
|---|---|---|
| 门的真跑 rc / 25 个阶梯夹具 | 全绿 | **全绿（逐位不变）** |
| 门的 `--selftest` 计数 | `{"bad": 0, "good": 122}` | `{"bad": 0, "good": 130}` |
| **合成夹具**上的 `same_file` | 4 | 4 |

也就是说：**如果只加「派生读数」的判据，这个缺陷永远测不出来**（这正是 R82
「门禁绿 = 恒等式成立 ≠ 覆盖度足够」的第二次应验）。于是 F10l 用两条**直接**判据：

| 半边 | 判据 | 为什么不能用更省事的写法 |
|---|---|---|
| **形态** | 产物在 `fan_in_top` / `fan_out_top` 里**自报**的 `file`，必须等于**夹具自己的**相对路径（`d1/x.c` / `d2/x.c`） | 不能比「读数的形状」—— 派生读数会一起错且自洽 |
| **不许静默** | **AST** 读 `_rel_of` / `build_c_model` / `_build_ext_model` 三个函数的 `root` **形参默认值**，`"NODEFAULT"` 才算过 | **不能**文本搜索 —— 注释里写「root 没有默认值」就能骗过它 |

配套夹具 `CG_DUPX_FIXTURES`：两个**不同目录**（`d1/x.c` / `d2/x.c`）各一份
`static int dup(void)` + 各自文件里的调用者。手推期望（**先于**跑产品写下）：
`edges_total=4`、`resolution = {unique:0, same_file:4, include:0, ambiguous:0, external:0}`。

**族内加半边 ⇒ 不触发六处级联**：签名串仍是 `F1–F10`，门数**仍 19**
（R85 定论：缺口为 0 时加闸 = churn）。坏样本 **48 → 56**（README 双侧、判据族表同步）。

## 5. 变异体 M14 / M15：两条决定各一个

| 变异体 | 注入什么 | 期望 | 实测 |
|---|---|---|---|
| **M14** | **完整**回退旧语义：`base = abspath(root)` → `abspath(getcwd())` **且**补回 `if r.startswith(".."): return basename(p)` | 只红 **F10l** | ✅ 三条红全落在 F10l（`same_file` 应 4 读到 0 / 留下 4 条歧义边 / 产物文件读到 `['x.c']`） |
| **M15** | 给三个函数的 `root` 补 `= None` | 只红 F10l 的 **AST 那半边** | ✅ |

**装置本身被修了两次**（两次都是「先问量具错还是对象错」）：

1. `inject()` 按 **LF** 归一计数、却在**原始 CRLF 字节**上替换 ⇒ 含换行的锚点
   **静默地一个也没替换** ⇒ M14 注入后**全绿**，看起来像「判据没有分辨力」。
   修法：读一次 / 在 LF 正文上全部替换 / 统一写回 CRLF。
2. 每个 `sub` 各录一份「原文」⇒ `restore()` 按录制顺序回写，最后落地的是
   **突变后**的内容 ⇒「还原后仍红」是**假红**。修法：每文件**只录一次**原文。

**M14 的第一版只换基准、不恢复塌陷** ⇒ 产物变成**第三种**形态
（`../../r88id_…/dup/cg_dup_a.c`），F10b 的覆盖半边拿**夹具 rel 名**比字符串 ⇒
连带红在 F10b。真相是**注入不忠实**，不是「判据多了」。改成完整回退后只红 F10l，
门里那句过强注释也随之改准（「23 个阶梯夹具**一个也测不出来**」→「没有一个能
**完整**测出来」，并把 ①/② 两条实测写进去）—— **改文档把真相写准，不放宽判据。**

## 6. 实测

### 6.1 合成夹具（R90a · 先于产品）
夹具：`alpha/x.c` + `beta/x.c`（**同 basename**，各一份 `static int helper`）+ `main.c`。
非规范形态用**兄弟目录**当 cwd、目标 `..\relfix`（**关键**：目标必须在 cwd 之外）。

| 读数 | 规范形态（修复前） | 非规范形态（修复前） | 手推期望 |
|---|---|---|---|
| `edges_total` | **6** | **6** | 6（4 个调用点，2 个各扇出 2 条）|
| `nodes_total` | **5** | **4** | 5 |
| `resolution.same_file` | **4** | **0** | 4 |
| `resolution.ambiguous` | **0** | **4** | 0 |
| `cross_file.internal` | **4** | **0** | 4 |

⇒ 机制成立：**同一份夹具**，只因调用者站的位置不同，给出两套数，而
`edges_total` **一条都没变**。修复后两形态**逐位一致**、且都等于**手推期望**
（`forms_differ_on: []`、`problems: []`）。

⚠ 量具的**第一版**把非规范形态选在「目标在 cwd **之下**」的目录里 ⇒ 塌陷不发生 ⇒
当时那条判据是**空判据**；同时手推 `edges_total` 漏了**扇出**（写 4，实测 6）。
**两次都是量具错**（`_r90/preregister_r90a.log` 里留着修正记录）。

### 6.2 真语料三层对账 + **第四条臂**（R90e）
语料 = CROSS 档 8 子树（与 R89 逐字相同），**3,927** 个 C 家族文件 / **68,030** 条边。
⚠ **「旧口径」列 = R90 之前的 `_rel_of`（cwd 相对 + 逃逸即 basename），且跑在形态 B 上**
—— 这就是塌陷态。下表若写箭头，一律「修复后 → 旧口径」。

| 量 | 形态A（规范） | 形态B（非规范） | **旧口径**（第四条臂） |
|---|---|---|---|
| `edges_total` | **68,030** | **68,030** | **68,030** ✅ 三臂逐位相同 |
| `nodes_total` | 22,647 | 22,647 | 22,546 |
| `resolution.same_file` | 2,370 | 2,370 | 2,273 |
| `resolution.include` | 2,034 | 2,034 | 4,059 |
| `resolution.ambiguous` | 19,553 | 19,553 | 17,625 |
| `cross_file.internal / cross` | 20,532 / 27,945 | 同 | 20,489 / 29,916 |
| **`cross_dir.internal / cross`** | **28,072 / 20,405** | 同 | **50,405 / 0** |
| 路径形态越界（`file` 不在根相对集） | **0** | **0** | **27** |

**两向都成立**：③ 两形态在产物读数的**全部 21** 个键上**逐位相同**；④ 第四条臂在**读数**与
**路径形态**两面都可分辨（`cross_dir.cross` 直接塌成 **0** —— basename 塌陷让
**每个文件都看起来在同一层**）。若第四条臂也相等，说明语料选错了、③ 是空判据 ——
这正是它存在的理由。

⚠ **预测半错，如实记在这里**：我预测塌陷会把边推给 `ambiguous`，实测它推给了
`include`（+2,025 = `include` 4,059 − 2,034），而 `ambiguous` 反而**少了 1,928**
（19,553 → 17,625）、`same_file` 少了 **97**（2,370 → 2,273）；97 + 1,928 = **2,025**，
三个桶的净变化**恰好为 0**（`unique` / `external` 一位没动）。
也就是说：**夹具上的机制是对的，但真语料上被另一条通路盖过** ——
夹具里根本没有 include 图。这条比「预测对了」更有用。

### 6.3 量具自己也被对账（R90e 的第一版为什么红）
第一版对账装置在真语料上红了两条：

```
RED PROJ 形态A 的 fan 有界投影被截断 ⇒ files_seen 不完整
RED PROJ 形态B 的 fan 有界投影被截断 ⇒ files_seen 不完整
```

追因：`callrel.py` 的 `fan_in_shown = min(top_n, len(fin))`，而真语料有 **22,647** 个
节点、`fan_in_total = 14,204` / `fan_out_total = 16,919` ⇒ **TOP-N 投影必然被截断**。
「有界投影必须完整」是**夹具尺度**的性质（3 个文件时装得下），写成判据就恒红。
⇒ **量具错，不是对象错。** 判据换成**直接**的形态判据（产物自报路径 ⊆ 本装置
自己数出的根相对路径集）；截断本身降级为**备忘**，文件全集由 ① 的
**产物自报** `summary.files` 承担（两本**独立**的账）。

v1 的原始读数**留着**（`_r90/reconcile_r90_dev1.log`）：「改正了量具」与
「放宽了判据」是两件事，账本必须能区分。

### 6.4 内核整树：**规范形态**上的跨轮回归（并且它否证了我的一个预测）

内核跑批（62,704 个 C 家族文件 / 36,155,901 行）的调用形态是 `cwd == 被分析根`、
目标 `.` ⇒ `relpath` 不以 `..` 开头 ⇒ **塌陷在数学上不可能发生**。
所以这一跑是修复的**阴性对照**：读数**一个都不该动**。

| 读数 | R89（上一行账本） | R90 | |
|---|---|---|---|
| `edges_total` | 7,060,966 | **7,060,966** | ✅ |
| `nodes_total` | 696,535 | **696,535** | ✅ |
| `std_funcs` | 743,509 | **743,509** | ✅ |
| `std_unresolved` | 1,295,143 | **1,295,143** | ✅ |
| `resolution` | `{unique 1,911,865 · same_file 381,290 · include 80,818 · ambiguous 4,686,993 · external 0}` | **逐位相同** | ✅ |
| `cross_file` | `{internal 1,041,930 · cross 1,332,043 · ambiguous 4,686,993 · unknown 0}` | **逐位相同** | ✅ |
| `json_bytes` | 11,355,506 | **11,355,506** | ✅ |
| 焦点子图 | 34 节点 / 19,469 边 | **34 / 19,469** | ✅ |
| `truncated` | `fan_in_total 448,003 · fan_out_total 599,314 · cycles_total 1,196`（shown 30 / 30 / 20） | **逐位相同** | ✅ |
| **`--callgraph` 产物** | 4,358,678 B · `sha16 78bd51d9…` | **4,358,990 B · `sha16 23dddd8b…`** | ⚠ **不等** |
| 跑次 | 1,290.1 s · 峰值 13,145.1 MB | **1293.1 s · 峰值 13,143.6 MB** | 墙钟差 **+0.2%**，**不归因**（R84 已定论：同臂相邻两次可差 **1.2×**）|

**⚠ 我预测错了一件事，而且错得有价值。** 我写下的判据是「产物**逐字节相同**」——
实测 **+312 B**。追因不是「还有别的东西进了图」，而是：

> R90c 把 `limitations` 里那条边界从「**已登记缺陷**」改判成「**已修 + 回归判据**」，
> 措辞变长（**291 → 455** 字符）—— 而 `limitations` **就在产物里**。
> 逐条现算：**唯一**变化的是第 7 条，UTF-8 长度差 **+312 B**，**恰好**等于实测差。

⇒ 判据改成 R87 的那条：**字节差必须被解释掉**。账本里现在是这样一条
**自算**的断言（`_r82/append_rounds_r90.py` 的 `limitations_delta()`）：

```
产物字节差（实测）  ==  用 HEAD 版与工作区版 callrel 各算一遍 limitations 的 UTF-8 长度差
```

不相等就红 —— 因为那意味着**还有别的东西**进了产物。
这条比「逐字节相同」**更弱也更对**：前者会把这个**正确的修复**判成回归。

> **R87 的教训在这里正着用了一次**：当时是「产物字节变了 ≠ 图变了」（体积全在被截断的
> 有界投影里）；这次是「图没变 ≠ 产物字节不变」（体积全在被改写的措辞里）。
> 两次都指向同一件事：**字节数与图是两个量，谁也不许单独当判据。**

### 6.6 最不起眼、也最危险的一条：**补丁会悄悄吃掉东西**

R90b 的补丁用「按缩进定位函数体」的方式整段替换 `_rel_of` —— 结果**连函数后面那
3 行注释 + 2 行空行一起吞了**（那是 `# ---- / # P90：语言前端插件化… / # ----` 分隔块）。
现有三道防线**全都看不见**：

| 防线 | 为什么看不见 |
|---|---|
| `ast.parse` / `--check-py36` | **注释不进 AST** |
| 门的真跑 + `--selftest` | 读数与计数**逐位不变** |
| `git diff` | 按同一套规则把两侧都归一化了 —— **它不是工具** |

看得见的只有**逐行对账**。于是新增一台仓外装置 `_r90/verify_patch_shape.py`：
对每个改动文件做 `SequenceMatcher`，把「HEAD 有、工作区没有的**注释行 / 空行**」列出来。

**判据：被删的注释行 == 0**，有意的改写要**逐条登记**（`EXPECTED_COMMENT_LOSS`）。
本轮扫 11 个文件：**只有 `matlabc.py` 命中**（3 注释 + 2 空行），唯一另一条
（`renderers/csite.py` 的一行注释）是**有意改写**并已登记。
修复后 `PATCH-SHAPE OK`。

> 这次是**补丁**咬了自己的正文 —— 两次都靠「别只看结论，看**逐行**」才看见。

## 7. 手一滑就会踩的四条（本轮新增）

1. **「改了量具」与「放宽了判据」必须能分开** —— 判据红了的第一个动作是
   **问它错在哪一边**，并且把**原始读数留档**。本轮红了**三次**（预登记量具的手推期望、
   对账装置的 `PROJ`、账本里的 `F10l` 断言），**三次都不是对象错**。
2. **判据的尺度要写进判据** —— `shown == total` 在夹具上对、在语料上恒假。
   凡是「完整性」类判据，都要先问**在什么规模上成立**。
3. **多行文本的补丁，锚点与核验都要先归一换行** —— 仓库 blob 是 CRLF、仓外草稿是 LF。
   本轮 `patch_docs_r90.py` 的核验拿 **LF 针**去扎 **CRLF 读回值** ⇒ 恒假 ⇒
   误报「新措辞不在位」（而文件其实**写对了**）。判据没错，量具错了。
4. **断言要钉在「失败态可得见」上，不是「成功横幅里有没有那个词」** ——
   我在账本里要求「门的成功行必须含 `F10l`」，而门的成功行只写**签名** `F1–F10`
   （子判据**只在红时点名**）⇒ 断言**恒假**（第三台量具坏）。改成
   「**注入缺陷时门的红输出必须点名 F10l**」（从变异体日志现算）——
   这比「成功横幅里有那个词」**更强**：它证明的是**这条判据真的会咬**，
   而不是「文件里出现过这个字符串」。
