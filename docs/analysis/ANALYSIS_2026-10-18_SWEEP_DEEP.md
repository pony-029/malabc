## §2 十一次判据错的根因图谱

按"为什么会错"分类，而不是按"错在哪"：

| 根因 | 次数 | 具体 | 为什么会发生 |
| --- | --- | --- | --- |
| **A. 字典返回 `None` 而不报错** | 5 | `files[].file`（实为 `rel`）、`model.uninit` | `d.get(k)` 对不存在的键返回 `None`，判据"通过" |
| **B. 约定凭直觉** | 3 | 空目录 rc=0（**错两次**）、`from-json` 页面数 | "空输入应当成功"听起来合理，实际相反 |
| **C. 开关形式凭印象** | 2 | `--fail-on-dup` 是 flag（实为带参）、`--quiet` 不存在 | 没查 `--help` |
| **D. 运行态当结果** | 1 | `stats.cache_*` 冷热不同 | 没区分"这次运行的状态"与"分析结果" |

**A 类是最大来源（5/11）**，而它**恰好是最容易用代码消除的**。

## §3 产品侧：一修、一发现、一不可归因

### 3.1 已修：`--lang c` 空目录 rc=0（R165）

```python
if not c_paths:
    _warn_unsupported_sources(root, args, "C/C++")   # 只 warn
c_model = build_c_model(c_paths, root)               # 继续
return _run_c_only(c_model, root, args)              # rc=0
```

**少一个 `return 1`**，代价是"路径拼错"看起来像"分析成功"。

**修复后四个分支统一为 rc=1，非空目录不变（rc=0）。**

### 3.2 已修：未知 LSP 方法回 `result:null` 而非 `-32601`（R167）

**并且这条修复顺带推翻了我上一轮的推断**：

> R166 我写：「服务端可能完全不回包（协议违规）」

**实测是 `{"id":9,"result":null}` —— 回包了，只是回的语义不对。**

**上一轮脚本卡住另有原因**：它在 `didOpen` 后等了**第三条**消息，而服务端只发两条。

### 3.3 未归因：并发两个 `--json` 时 180 秒超时

**这次测量不干净** —— 62,704 文件的探针同时在跑。**不能写成"并发死锁"。**

**判据**：探针结束后，空闲机器上两个进程都应在 5 秒内返回。

## §5 系统性改进：从"逐条修"到"结构性防护"

**11 次判据错如果逐条修，下次还会犯。** 所以按根因归并成三条代码级防护：

| 防护 | 对应根因 | 实现 |
| --- | --- | --- |
| `shape_of()` + `need()` | **A（5 次）** | 取字段前断言它存在，否则打印真实 keys |
| `EMPTY_INPUT_RC = 1` 常量 | **B（3 次）** | 约定只定义一次，不在每个判据里重新假设 |
| `canon()` 剔除 `generated_at` / `stats.cache_*` | **D（1 次）** | 明确"运行态"与"结果"的边界 |

**C 类（开关形式）没有防护** —— 它只能靠"先跑 `--help` / 先 `--version`"这个纪律。

**`--selftest` 7 条**守的就是这三条防护自己：防护写错时，全量跑会**全绿而什么都没测**。

## §6 三条可复用的法则

### 法则一：新判据第一次跑就红时，先怀疑判据

86 个检查点里，**产品只错了 1 处**（`--lang c`），而**判据错了 11 次**。
如果顺序反了（先怀疑产品），会去"修"十一个正确的实现。

### 法则二：一次「卡住」比十条「通过」信息量更大

第 8 轮没跑完，但它逼出了 `-32601` 这条修复。**测试报告里"为什么没测完"
应该和"测出了什么"一样重要。**

### 法则三：记录问题不等于解决它，但也不等于可以马上改

`--lang c` 从第一轮记录到第五轮才修，`--from-json` 的宽松至今未改。
**"已知不一致"必须有到期日**，否则它会变成永久的免责声明。
**判据**：每次记录时同时写下"什么条件下可以改"。

### §11.1 第 8 轮：LSP 对各种畸形输入都不崩

| 输入 | 结果 |
| --- | --- |
| `initialize` **不带 rootUri** | 正常返回 capabilities |
| 打开**非 `.m` 文件**（`.txt`） | 两条诊断，均空 |
| 打开**不存在的文件** | 两条诊断，均空 |
| **未知方法** `workspace/symbol` | **`-32601`**（R167 修的） |
| 未知**通知**之后 | `shutdown` 仍有响应，连接存活 |
| `rootUri` 指向**空目录** | 正常，0 诊断 |

**这 12 条证明的是"健壮"，不是"功能对"** —— 功能对由另外 19 条证明。
**一个 LSP 如果对畸形输入崩掉，功能再对也不可用。**

**顺带澄清 R166 的误判**：当时脚本"卡住"不是因为服务端不回包，而是因为
它等**第三条**消息（`didOpen` 只发两条）。**带超时 + 只等两条之后，12 条一次通过。**

### §11.2 第 9 轮：四格式数字一致，但 **SARIF 少了 `m_missing_doc`**

| 对照 | 结果 |
| --- | --- |
| XML `<stats><files>` vs JSON `stats.files` | 一致 |
| XML `<stats><functions>` vs JSON | 一致 |
| mermaid 节点数 vs JSON `functions` | 一致 |
| browse 首页提及的文件数 | 含 `13` |
| **SARIF `results` vs `heuristics`** | **1 vs 5** |

**根因**：SARIF 的 `rules` 里有 `uninitialized` / `dead_code` /
`c_heuristics` / `py_heuristics` / `js_heuristics`，**没有 `m_heuristics`**。

⇒ **用 GitHub Code Scanning 的 CI 看不到「函数缺 description」。**

**这不是崩溃，是覆盖范围不同**：`heuristics` 与 `checks_for_sarif` 是
**两个类别**，不是超集关系。**已记录为已知缺口，未改** ——
要不要把 `m_missing_doc` 塞进 SARIF 是一个产品决定（note 级别该不该上报）。
