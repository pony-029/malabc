## 1. 黑帽 · 这套测试还会怎么失效

1. **修了但没锁**：R362 改了两处错误文案，**没有任何判据守着** ——
   全场景里那条断言是 `A or B` 的宽松形式，改回去也不会红。（本轮已补）
2. **覆盖不均**：16 条变异 vs 200 条判据 = **8%**；58 个场景里 MCP 只覆盖
   19 个工具中的 12 个。
3. **全是合成语料**：跨语言只用 2~3 个手写 `.c`；真实 `mex` / `dll` 未测。
4. **无 UI 层验证**：`extension.js` 只有括号配平，面板/展开态/跳转全靠人眼。
5. **无时间维度**：性能只有阈值断言（如 outline < 30s），**没有历史趋势**，
   所以「从 0.3s 慢到 20s」不会被任何人发现。
6. **无并发/长跑**：所有场景都是单进程、单次、短时。
7. **错误路径只锁了 3 条**：全仓约 50 处 `_err(...)`，其余没判据。

## 4. 蓝帽 · 一句话结论

> **这套测试已经能挡住“改坏”，但挡不住“漏写”。**
>
> 200 条判据 + 32 道门 + 58 个场景，说明**已实现的东西不容易退回去**；
> 而 README 里整整六轮的跨语言能力一个字都没有，说明**“有没有做”与
> “别人知不知道”之间没有连接**。
>
> 下一步的重心应从“更严的判据”转向**覆盖面均摊**（第 5、6、9 条）
> 与**可见性**（第 4、18、19 条）。

### 6.2 上传后立刻发现的文档缺陷（两处，同一行）

README 最后一行是：

```
Plain-tool note: \tools/incremental_parity.py checks ... (\x07nalyze(prev=, changed=)) ...
```

两个问题叠在一起：

1. **转义吃字**：R226 的脚本把 `python tools/...` 里的 `\t` / `\a` / `\b`
   当成转义处理，于是 `python tools/` 变成 `\tools/`、`analyze` 变成 `\x07nalyze`。
2. **陈述过时**：那句写着"增量校验**现在是红的**"，而 `check_incremental_parity`
   早就全绿了 —— **文档在控诉一个已经不存在的缺陷**。

两处都跨了上百轮没人发现：因为它在**文件最后一行**，而所有门读的都是表、
章节、代码围栏 —— 没有门读“最后一句”。
