# 设计：用一个语义核心统一 `mir` / 发射器 / `unmir`（R688）

> 本文只做设计，不写产品代码。所有数字来自仓库里可复现的测量。

---

## 一、现状：管线里有**三份各自为政的"真理"**

一次转换实际经过四个环节，而"什么叫一个算子"在其中被**独立定义了三遍**：

| 环节 | 模块 | "算子"在此处的定义 | 实现方式 |
|---|---|---|---|
| ① MATLAB → MIR | `translate/mir.py` | `parse_line` 里的一串**正则** + `_UNARY_LINE`/`_PRED_LINE`/`_MOD_LINE`… | 手写模式匹配 |
| ② MIR → C | `rust/m2c/src/emit.rs` | `C_IMPLEMENTED` 白名单 + **每个算子一段手写分支** | 手写 Rust 分支 |
| ③ C → MIR | `translate/cmir.py` | 从 Python 算子表反查 `c` 字段 | 反向查表 |
| ④ MIR → MATLAB | `translate/unmir.py` | 又一张 `_BIN`/`_FN` 映射表 | 手写映射 |

**同一件事写了四遍。** 于是：

- 新增一个算子要改 **5~7 处**（C 实现、头文件、算子表、`parse_line` 正则、`_UNARY_IDS` 映射、Rust 白名单、`unmir` 映射、文档）；
- 每处漏一处，功能就**静默不生效**（R675、R683、R676 都是这样翻车的）；
- `cmir` 认不出 `mlc_op_size_all` 时，看起来像"发射器丢算子"（R668）。

### 证据：最近 6 轮里，一半时间花在"接线"而不是"能力"

| 轮次 | 目标 | 卡在哪 |
|---|---|---|
| R675 | `isinf/isnan/prod/mod` | 表项加了但 `parse_line` 不读它 → 退回 |
| R676 | 同上 | 找到真因：`parse_line` 是显式正则，要改**两处** |
| R683 | 参数 struct | 展开了，但 `reject:struct` 还在（另一处判据） |
| R668 | 三段对拍 57/58 | `OP-SIZE` 有两个 C 入口，表里只登记一个 |

## 二、为什么"映射不完全"是**结构性必然**，不是勤勉问题

三个原因，任何一个都足以让覆盖率永远停在某个数字上：

### 1. 匹配是**语法**的，缺信息
`parse_line` 只看一行文本。它分不清：
- `x(1)` 是数组下标还是函数调用；
- `s.f` 是结构体字段还是对象属性；
- `ones(2,3)-x` 里的 `ones` 是构造还是某个同名变量。

任何"看起来该支持"的写法，只要正则没覆盖，就落进 `unmapped` —— **而原因只剩一个桶名**（`call2`/`struct`/…），不带签名、不带期望类型。

### 2. 能力是**分散声明**的
"支持 `sum(x,2)`"这件事，在四处各写一次。所以"支持"这个词没有唯一定义：
`parse_line` 支持 ≠ 发射器支持 ≠ `unmir` 支持。R668 的三段对拍就是在测这三个定义是否一致。

### 3. 边界是**隐式**的
MATLAB 是动态类型，C 不是。`varargin`、cell、结构体数组、动态字段名，这些**必须由人声明**边界。
但今天的做法是：解析器遇到它们就**整体拒绝**（YALMIP 2185 个函数里 1044 个，48%），
而拒绝理由是一句 `reject:varargin,cell` —— 用户不知道"改成什么样就能转"。

## 三、通用语义框架：**Semantic Core + 能力登记表 + 边界契约**

核心思想一句话：

> **"一个算子是什么"只在一处定义；三端都从这一处派生，而不是各写一遍。**

### 3.1 Core IR：带类型的操作序列

```
func: snr(arg sig: f64[4], noise: f64[4]) -> (y: f64[1])
  v1 = op.mul(sig, sig)                 # 逐元素
  v2 = op.mean(v1)                      # 归约
  v3 = op.div(v2, v4)
  v4 = op.add(v5, const 1.0)
  ...
```

与今天的 MIR 相比，三处关键增强（都只为"消除不完整"服务）：

| 增强 | 解决什么 |
|---|---|
| **SSA（每个值只赋值一次）** | 消除 `set:` / `setb:` / `op:` 三套写法的歧义（R683 的"假算子"就来自这层混乱） |
| **每个值带 kind**（`scalar` / `vector[n]` / `matrix[r,c]` / `record{f1,f2}` / `cell`） | 让"未声明"变成**编译期错误**而不是运行期静默 |
| **每个 op 带签名**（`op.mean(vector) -> scalar`） | 归因从"桶名"变成"**期望 vector，实际 record**" —— 用户能照做 |

> 关键：kind 不需要完整的类型推导，只需要**边界声明 + 局部传播**。
> 现有 `% @m2c shape x 5` 就是这个思路的特例，框架把它推广成 `kind`。

### 3.2 能力登记表：**唯一事实来源**

每个算子**只登记一次**：

```yaml
- id: mean
  sig: "mean(vector) -> scalar"          # 语义签名（用于类型检查与归因）
  c:   mlc_op_mean                       # 目标实现（发射器据此生成调用）
  c_aliases: [mlc_op_mean_alloc]         # 同一算子的其它 C 入口（R668 的坑）
  matlab: ["mean(x)", "mean(x,dim)"]     # 前端可识别的形态（**供人读**，不再是匹配依据）
  unmir: "mean({0})"                     # 回译模板
  tags: [reduction]
```

三端都**只读这张表**：

```
        ┌──────────────── 能力登记表（唯一事实来源） ────────────────┐
        │  sig / c / c_aliases / unmir / tags                        │
        └───────┬──────────────────┬──────────────────┬─────────────┘
                │                  │                  │
      MATLAB → Core          Core → C            C → Core
    （按 sig 做匹配与       （按 c 生成调用，     （按 c 反查 id，
      类型检查）            不再手写分支）        天然一致）
```

**这一步就能消掉 R675/R676 那一类失败**：不再有"表里有、正则不认"的状态，因为正则不再是判据。

### 3.3 边界契约：把"隐式拒绝"变成"显式声明"

```matlab
function y = f(cfg, x)
% @m2c record cfg { gain, offset }        % 结构体（一组标量）
% @m2c kind x vector[4]
% @m2c kind y vector[4]
```

| 今天的做法 | 框架的做法 |
|---|---|
| 遇到 struct/cell/varargin → **整函数拒绝** | 边界必须**声明**；未声明 → 报错并**给出可粘贴的声明** |
| 拒绝理由 `reject:varargin,cell` | `第 3 行参数 v 使用 varargin：改成显式形参，或声明 % @m2c variadic v` |

这与已经落地的 `check --annotate`（R685）是同一条路，只是把它从 struct 推广到**所有边界**。

### 3.4 归因：从"桶名"到"可行动的句子"

今天：`unmapped: y = sum(abs(x.basis),2)>0;`（类别 `call2`）
框架：

```
第 5 行  op.sum 的期望签名是 sum(vector) 或 sum(vector,dim)，
        实际第 1 个实参是 record{x.basis: matrix}，第 2 个是常量 2 → 匹配 mean 失败
建议：先取 x.basis 再求和 → y = sum(abs(x_basis), 2)
```

这类输出的价值已经在 `check`（R678）里验证过：105 处行号核对 104 处吻合。

## 四、框架**能**与**不能**解决什么（诚实边界）

| 问题 | 框架能解决？ | 说明 |
|---|---|---|
| 新增算子要改 5~7 处 | ✅ 改 1 处 | 登记表 + 派生 |
| "表里有、正则不认" | ✅ | 正则不再当判据 |
| 归因只有桶名 | ✅ | 签名 + 实际类型 |
| `s.f` 是字段还是属性 | ✅ 部分 | 靠边界声明；无声明仍拒绝（正确） |
| `varargin` 动态分派 | ❌ | C 侧无自然映射；只能**声明后**变成固定参数列表 |
| 动态字段名 `s.(name)` | ❌ | 运行时键；只能拒绝并说明 |
| 元胞数组 `c{i}` | ❌（本版） | 需要真正的容器类型；不建议做 |
| 大库全自动移植 | ❌ | 这是**边界**问题，不是框架问题 |

**一句话**：框架把"不支持"从**沉默的失败**变成**可读的、带建议的拒绝**；
它不会让动态语言的全部特性变成静态可编译 —— 那是不可能的。

## 五、三条路线

| 路线 | 内容 | 成本 | 风险 | 收益 |
|---|---|---|---|---|
| **A 继续现状** | 每轮补算子/补正则 | 每轮 1 个 | 低 | **已证伪**：R686 普查显示"只差一条"的 80 个函数里没有共同算子 |
| **B 全量重写** | 直接从 Core IR 重做三端 | **12~15 轮** | 高（管线全断，回归要重建） | 一次性彻底 |
| **C 增量收敛（推荐）** | 保留现有 MIR 文本格式，**逐步把三处硬编码改为查表**；每步三段对拍必须仍 58/58 | **5~6 轮** | 低（每步可回退） | 拿到 B 的 80% 收益，且不需停摆 |

### 为什么推荐 C

1. **现有资产是硬的**：语料 58/58、三段 58/58、往返 55/55、相互转换 58/58 —— 全量重写要从零重建这些。
2. **失败成本不对称**：C 每步只改一处，红灯就回退一步；B 中途红灯无处可退。
3. **最痛的那部分（登记表）本来就可以先做**：它是纯增量，不改变外部行为。

## 六、分阶段计划（每阶段都有可量化的判据）

| 阶段 | 内容 | 轮次 | 判据（必须量化） |
|---|---|---|---|
| **S1 登记表归位** | 把 `parse_line` 的正则、`_UNARY_IDS`/`_PRED_IDS`、`unmir` 的映射，**全部改为从算子表派生**；表里新增 `sig` / `unmir` / `c_aliases` 字段 | 2 | ①三段对拍仍 58/58；②删掉至少 3 张手写映射表；③新增一个算子只需改 1 个文件（写一条判据验证） |
| **S2 归因升级** | `unmapped` 记录**算子签名 + 实参 kind**，`check` 输出"期望/实际"对照 | 1 | 抽查 20 条诊断，全部能说出"期望什么类型、实际是什么" |
| **S3 边界契约推广** | `% @m2c record` / `shape` 统一为 `kind`；`check --annotate` 覆盖 record/cell/varargin 三类建议 | 1~2 | 未声明而被拒的函数，**100% 附带可粘贴声明** |
| **S4 用契约重测** | 对 YALMIP 的 115 个"只差 struct"与 80 个"只差一条"批量出声明，量翻转 | 1 | **翻转数 ≥ 40**（当前 26） |
| **S5 收口** | 把"框架能/不能"写进 `check` 的拒绝理由；发版 | 1 | 拒绝理由全部可行动；`task_kpi` 基线进 CI |

**总计 6~7 轮**，每轮都能停、都能回退。

## 七、风险与止损

| 风险 | 止损 |
|---|---|
| S1 改派生时把现有行为改坏 | 每改一张表前先跑三段对拍；红灯立即回退该表 |
| `sig` 设计过细，变成半个类型系统 | **硬边界**：sig 只允许 `scalar / vector / matrix / record / cell` 五种 kind，**不做泛型、不做推导链** |
| 为了"统一"而引入新 IR，导致 unmir/cmir 全部重写 | **不做新 IR**：沿用 MIR 文本格式，只替换"谁定义算子" |
| 翻转数上不去，白忙 6 轮 | S4 是**中途检查点**：若翻转 < 30，停在 S3 并把结论写进设计文档，不继续 |

---

## 八、与已批准计划的关系（不推翻，只加速）

`docs/DESIGN_TOPLEVEL.md` 的阶段 1（`check`）、阶段 2（`task_kpi`）已完成，阶段 3（struct）进行到 26 翻转。

本设计**不改变**那条路线，只是指出：**阶段 3 之后如果继续按"补算子"走，会撞上第二阶段普查已经证明的天花板**（80 个"只差一条"没有共同算子）。
所以 S1~S3 应该**与阶段 3 并行**——它们是"把已有能力接对"，而不是"加新能力"。

---

## 九、一句话总结

> **不要再用"多支持一个函数"来换覆盖率；要让"支持"这件事只有一处定义，
> 并把"不支持"变成一句用户能照做的说明。**
