# R86-3 复盘 — 把「调用边」从**计数**变成**关系**（用户实测反馈驱动的一轮）

> 起点是**用户的一句话**，不是自查：「内核分析结果并没有体现出函数之间的调用关系」。
> 本轮范围：新增 `callrel.py` + `--callgraph` 四开关 + 门禁判据族 **F7** + 内核真跑交付；
> **产品分析路径的 JSON 载荷一行未动**（下面 §1.4 有逐字节证据）。

## 0. 一句话

调用边**一直在算**（内核整树实测 7,065,831 条），但**没有任何产物承载它** ——
`--json-level summary` 的载荷**结构上不含 `edges` 数组**（只写 `summary.edges` 这个计数），
而全量数组在内核规模下是 GB 级。用户拿到「结果」，看到的只有数字。
本轮补上第三条路：**有界投影**（顶层恒为 KB 级 + 截断如实上报 + 焦点子图按需展开）。

## 1. 白帽 —— 事实

### 1.1 根因钉在一行上

`matlabc.py` 的 C 载荷分两支：

| 档位 | 顶层键 | 有没有「谁调用谁」 |
|---|---|---|
| `--json-level summary` | `lang / version / json_level / annotations / files / summary / heuristics_by_kind / asm / comment_stats` | **完全没有**（只有 `summary.edges` 计数） |
| 其余档位 | 多出 `edges` / `include_edges` / `unresolved` / `heuristics` | 有，全量 |

⇒ 这是**呈现 / 档位语义**缺陷，**不是数据缺失**。代价可直接量：我上一轮为了控体积
刻意选了 `summary`，于是 **11,355,505 B 的产物里一条关系都没有**。

另外查实一处**能力不对等**（此前无人登记）：MATLAB 路径有 `--mermaid` / `--dot` /
`--file-graph` / `--folder-graph` 与首页力导向调用图；**C / Py / JS / ASM 路径一个都没有**。

### 1.2 交付形状：三档并存，各自说清边界

| 档 | 内容 | 规模相关性 |
|---|---|---|
| **结构层** | `fan_in_top` / `fan_out_top` / `cycles`（名字级 SCC）/ `cross_file` / `cross_dir` | **与语料规模无关**（恒 KB 级） |
| **子图层** | `--callgraph-focus <名>` + `--callgraph-depth N` + `--callgraph-max-nodes N` | 由**上限**决定，不由语料决定 |
| **截断层** | `truncated.*_total` 与 `*_shown` 并列；BFS 撞上限置 `hit_node_cap` | 显式 |

三条口径**写成字面量**（进 `limitations`，且被 F7f 钉住）：
① 节点身份 = **被调函数的名字**（`identity: "callee-name"`），**不是定义落点** ⇒
跨文件同名会合并、`cycles` 可能含**假阳性**；② 未解析调用**不在图里**（没有 callee 节点），
只并列报计数；③ 截断永远显式 —— 「我没展开」不等于「没有关系」。

### 1.3 探针两向 + **分辨力**（绿本身不是证据）

`_r82/probe_callrel.py`：**46 条断言，0 失败**。
`_r82/mutate_callrel.py`：**6 个变异体，全部「注入即红且可追溯」，还原即绿**。

| 变异体 | 注入 | 变红的断言 |
|---|---|---|
| M1 | `truncated.fan_in_shown` 报成全量 | 1 条（截断说谎） |
| M2 | SCC 只报 size>2 的环 | 2 条 |
| M3 | `ambiguous` 并进 `cross`（口径塌陷） | 1 条 |
| M4 | 子图不设节点上限 | 3 条 |
| M5 | caller 方向整条失效 | 2 条 |
| M6 | 层次值恒为 1（集合不变、字段说谎） | 1 条 |

**三个被变异测试揪出来的、我自己的错**（这一节的价值比 46/46 高）：

1. **M2 暴露出探针会「崩」而不是「红」** —— 漏报时 `cyc[0]` 抛 `IndexError`，
   于是后面 20 多条断言**一条都没跑**，而调用方只看退出码：两者长得一模一样。
   ⇒ 加了 `sys.excepthook`：崩溃必须打 traceback **并**补一条 FAIL 行。
2. **M5 暴露出我写了一条空断言** —— 「focus=`a`、方向=caller ⇒ 只有自己」这条
   在**关掉整个 caller 分支**时**照样成立**（`a` 本来就没有调用方）。
   ⇒ 对手方换成「caller 与 callee 结果**必须不同**」的那个点（以 `c` 为中心）。
3. **M6 暴露出「只比集合」的断言对层次字段完全失明** —— 层次值恒 1 时节点集合一个不变。
   ⇒ 补上逐点层次值断言。

**还有一次「陈旧的红」**：我重写 `focus_subgraph`（见 §1.5）后，M4 / M5 的**锚点**失效，
变异装置当场报「锚点命中 2 次 / 0 次」——它自己就是「陈旧登记」的对手方。

### 1.4 门真的开火 **6** 次（1 次预期 + 5 次真问题）

| # | 触发 | 门报什么 | 是真问题吗 | 处置 |
|---|---|---|---|---|
| 1 | 装门即跑（**预期红**） | `F7 没有自己的坏样本（覆盖静默缩水）` | 否（纪律验证） | 补 16 个坏样本 + 2 条夹具完备性两向 |
| 2 | 改完签名 | `H1 rc=0 的描述里逐字找不到签名 'F1–F7'` | **是** | 描述写成含 `F1–F7` 字面量 |
| 3 | 加 CLI 开关 | `R5 / R5c --help 漂移 +1631 / +1299 字节` | **是**（合法增长） | 同一提交里更新两条快照 + 写理由，`HELP_DRIFT_BYTES` **一个字不动** |
| 4 | 全量门禁 | `check_kernel_snapshot W2 sha256/bytes 陈旧` | **是** | 内核**真跑**（不是改表） |
| 5 | 我改 `matlabc.py` 后 | W2 再次陈旧 | **是** | 先用**最终版**跑，再重生成登记表 |
| 6 | 自查（不是门） | 新产物 `kernel_callgraph.json` **不落在任何登记处** | **是** | 生成器新增「运行产物」表（字节 + sha256 逐个现算），文档级 `--check` 做对手方 |

**第 6 条值得单独说**：门全绿**不等于**没缺口。`check_kernel_snapshot` 的产物链检查的是
**站表 in/out 的拓扑**，不是「目录里有哪些文件」—— 所以一份新产物可以**存在但无人登记**，
删掉它没有任何东西会响。这正是「门禁绿 = 恒等式成立 ≠ 覆盖度足够」（R82 定论）。

### 1.5 内核真跑（交付读数）

| 项 | 读数 |
|---|---|
| `matlabc.py` 指纹 | sha256 `95fabb12976167ee…`，1,647,973 B |
| C 臂 | `rc=0`，**534.4 s**，峰值 **13,137.0 MB**，62,704 文件 / 743,518 函数 |
| C 臂 JSON | **11,355,505 B** —— 与改造前**逐字节相同**（见下） |
| ASM 臂 | `rc=0`，2.6 s，峰值 142.6 MB，486,229 B |
| 与 R81 对照 | C 臂 10 个字段全等、`diff {}`；ASM 臂 4 个字段全等 |
| **新产物** | `kernel_callgraph.json`，**1,313,559 B**，sha256 `a94016b5139ada70…` |

**`json_bytes` 逐字节不变是本轮设计的关键证据**：`--callgraph` 走**另一条出口**，
不往 `summary` 载荷里加块 —— 否则「分析结果没变」与「产物变长」会混成同一个数字，
而那本账（`provenance` 对 R81 的逐位对账）就再也不能回答「分析结果还没变吗」。

**有界投影读出来的东西**（这是用户真正要看的那一份）：

| 项 | 读数 |
|---|---|
| 图 | 645,191 个节点 / **7,065,831** 条边 / 未解析 1,295,146（**不在图里**） |
| 扇入 TOP | `memcpy` **546,567** · `memset` 403,146 · `test` 204,102 · `kfree` 161,808 · `writel` 155,764 · `mutex_unlock` 143,725 · `mutex_lock` 136,584 |
| 跨文件四桶 | 内部 660,640 / 跨文件 1,251,229 / **同名多定义（不猜）5,153,962** / 无定义 0 —— **四桶之和 == 7,065,831** ✓ |
| 调用环 | **908** 个，环内节点 41,009，最大环 **37,776** |
| 次大环 | 84（MPTCP）· 66（nilfs2 bmap/btree）· 66（JFFS2）· 50 · 42（rtw89）—— 看着就是**真的**互为递归子系统 |
| 截断 | 扇入 30/430,640 · 扇出 30/571,434 · 环 20/908 |

**最大环 37,776 与「同名多定义占 72.9%」是同一件事的两面**：名字合并把无关子图缝在一起，
于是出现一个巨大的伪环。**三条 `limitations` 里第一条说的就是这个** —— 它没有被藏起来，
它就在产物第一行。次大环的四个（84 / 66 / 66 / 50）与最大环差**两个数量级**，
这个断层本身就是「有一个是假的」的信号。

### 1.6 顺带露出来的**真缺陷**（新的东西不该只有「能看见」这一个收获）

提示词子图里出现了 `__attribute__` 作为一个**被调用函数**。追下去：

```
drivers/gpu/drm/amd/pm/swsmu/inc/pmfw_if/smu_v13_0_12_pmfw.h:196
typedef struct __attribute__((packed, aligned(4))) {
```

被 C 前端解析成一个**函数定义**：`name=__attribute__`、`ret='typedef struct'`、
`params=['(packed, aligned(4))']`、`body 196→294`。

**两套独立口径互相印证**：
* 对源码 grep `typedef\s+struct\s+__attribute__` ⇒ **2 个文件、7 处**；
* 前端输出里名字为 `__attribute__` 的「函数」⇒ **7 个**（`smu_v13_0_12` 3 个 + `smu_v13_0_6` 4 个）。

而那 2 个文件里被认出的「函数」**总数就是 7** ⇒ 这两个文件的函数表 **100% 是假的**。
对照口径：`include/linux`（16,922 个函数）**0 例** ⇒ 缺陷是**特定模式**触发的，不是遍在的。
内核级占比：**7 / 743,518 = 0.0009%**（计数可忽略），但它**造出一个跨文件合并的伪节点**，
性质是「口径错」而不是「少算」——R83 定论：口径类缺陷比功能类危险。

这条**此前不可能被看见**：F1–F6 用的是我自己手写的合成夹具，里面不会有这个模式；
只有把真实内核的调用图打出来，它才浮上来。**修呈现缺口不只是「让用户看见」，它让新的缺陷变得可见。**

### 1.7 缺什么数据（白帽必须报）

* **缺陷的内核级全量**没测：要 `--json-level full` 才有全部函数名，那是 ~2.6 GB。
  目前只有「2 文件 / 7 处」与「`include/linux` 0 例」两个**端点读数**，中间没有分母。
* `--callgraph` 的 **Py / JS / ASM 路径**只做了小夹具冒烟（Python 夹具环 `hub ⇄ leaf` 命中），
  没有整树级读数。
* **GUI 没有入口**：本轮把开关加进了 CLI 与帮助，但 `gui.py` 的卡片没跟上
  （R86-2 曾为二进制诊断加过卡片，这里是**新的不对等**）。
* `kernel_callgraph.json` 已进 `docs/KERNEL_RUN.md` 的「运行产物」表，但**不在 AGG 里** ——
  删掉它会让文档 `--check` 变红（有对手方），但 `AGG_r84.json` 本身仍不知道它存在。

## 2. 红帽 —— 直觉

* 用户那句话我第一反应是「数据在，只是我没给你看」—— **这是个很差的辩解**。
  用户收到的东西就是「产品」，产品里没有调用关系，那就是**产品缺陷**。
* 更刺的是 §1.5 的三个数：**同名多定义占 72.9%**、**最大环 37,776**。也就是说这一轮
  交付的图，在**内核这种重名重灾区的语料上，四分之三的边连不上文件**。
  功能是对的、纪律是对的、读数全部自洽 —— 但离「有用」还差一层身份消歧。
  这种「全绿但不够有用」的感觉，比一个红更让人不安。
* §1.6 那个 `__attribute__` 让我有点后怕：F1–F6 那六条判据守了五轮，从来没碰到它。
  **合成夹具永远只会验证你想得到的东西。**

## 3. 黑帽 —— 风险

| # | 风险 | 最坏情况 | 现有对手方 | 缺什么 |
|---|---|---|---|---|
| **B1** | **名字级身份被当成定义级用** | 有人拿 `cycles` 当「这里真递归」的结论去改内核，而最大那个环是假的 | `identity` 字面量 + `limitations[0]` + F7f | 没有**量化**的告警（比如「同名多定义占比 > X% 时在终端显著提示」） |
| **B2** | **有界投影被当成全量** | 用户看到扇入 TOP 30，以为只有 30 个热点 | `truncated` 的 `*_total` 并列 | 终端那行 `截断：扇入 30/430640` 太轻，容易被划过去 |
| **B3** | **焦点子图的「双向 + 深度 2」在小图上爆边** | `both` 方向从一个 300 出度的函数出发 ⇒ 子图边数 ~O(N²) | `max_nodes` 只管节点，**不管边** | **边数没有上限** —— 这是个真口子（本轮内核上 `memcpy` 只 128 条边，没触发） |
| **B4** | **`--callgraph` 的产物没有进 AGG** | 删掉产物，只有文档 `--check` 会红，AGG 那本账沉默 | 文档 `--check` | 产物级登记（sha256）应进 AGG 键 |
| **B5** | **帮助体积快照再次漂移** | 下一轮再加开关时忘了同步 ⇒ 陈旧的红 | 门 R5/R5c + 记账注释 | —— |
| **B6** | **改名 `focus_subgraph` 之类会失效变异锚点** | 变异测试静默退化成「锚点找不到就跳过」 | 本装置**要求锚点恰好命中 1 次**，否则整体判问题 | —— |

## 4. 黄帽 —— 价值

* **用户直接点名的缺陷被解决**，而且交付物是**打开的**：`kernel_callgraph.json`
  里第一眼就是 `memcpy 546,567 次被调用`、`908 个调用环`。
* **一套投影，五条语言路径共用一个出口**（`_emit_call_relations` 同时接在 C 与
  Py/JS/ASM 上），没有为第二处再发明一遍。
* **内存纪律经得起规模**：`array('i')` 的 CSR（不是 `dict[str, list]`）、逐层重扫
  （不是常驻邻接表）。内核峰值只从 13,072.9 → **13,137.0 MB**（+0.5%），
  却多算了 7M 条边的强连通分量。
* **「另一条出口」这个设计决定**同时保住了两件事：新能力交付了，
  `json_bytes` 一个字节没动 ⇒ 既有的 R81 对账**继续有效**。
* **新缺陷可见**（§1.6）：修呈现缺口的回报溢出到了「发现新缺陷」。

## 5. 绿帽 —— 替代方案与改进点

* **方案 A：把 `edges` 塞进 `summary` 档。** 否 —— 11 MB → ~950 MB，用户的机器先炸。
* **方案 B：照搬 MATLAB 的 `--dot`。** 不够 —— 内核上 DOT 本身也是 GB 级，
  且它不回答「环在哪、枢纽是谁」。
* **方案 C（采纳）：结构层 + 子图层 + 截断层，三档并存。** 理由是它同时满足
  「任意规模可读」「体积可控」「每一档都有对手方可裁决」。
* **没采纳但值得做的**：`--callgraph-top-n`（现在恒 30，写死在常量里）；
  `--callgraph-max-edges`（B3 那个真口子）；把 `cross_dir` 升成一张**目录级矩阵**
  （现在只有三个计数，信息密度太低）。

## 6. 蓝帽 —— 综合结论

* **是真缺陷，且是「呈现 / 档位语义」缺陷**，不是数据缺失。根因一行可指。
* 黑帽 B1/B2 与黄帽「任意规模可读」互相拉扯 ⇒ **唯一出路是有界投影 + 口径字面量 +
  截断显式**，本轮就是这么做的。
* **最重要的产出不是那张图，而是三个「绿以外的证据」**：变异测试揪出我自己两条
  空断言 + 一条崩溃式失败；`json_bytes` 逐字节不变证明「新能力没污染旧账」；
  `__attribute__` 证明「修呈现缺口能让旧缺陷浮上来」。
* 最大的**未解决**问题是同一件事：**名字级身份**。四分之三的边连不上文件，
  最大那个环是假的。这一条不是「再优化一点」，它是**下一层的入口**。

## 7. 下一步（R87，按价值排序）

1. **符号级身份（definition-site）** —— 最有价值的一条。把节点从「名字」换成
   「文件+名字」（至少对**同名多定义**的那些名字做），`ambiguous` 那一桶
   （内核 5,153,962 条，72.9%）就会塌下去，而最大伪环 37,776 应当**当场散架**。
   出口判据要能两向：**同名多定义占比必须下降**，**且** `ambiguous` 桶**只准变小**，
   **同时** `cycles` 的最大分量必须从 37,776 掉到 ≤ 三位数 —— 只断言「环变少了」
   是可以靠**整类不报**刷出来的（R83 定论①）。
2. **`__attribute__` 假定义**（§1.6）—— 真缺陷、有 7 处现成夹具（那 2 个文件）。
   修法：定义扫描器把 `typedef struct <attr>(...) {` 排除；出口判据挂进 F1–F6 那一族
   或新开 F8，并把这 2 个文件的实际片段做成**合成夹具**（不引内核，仓内可跑）。
3. **`--callgraph-max-edges`**（黑帽 B3）—— 现在 `both` 方向只有节点上限，
   边数无上限。补上限 + 撞上限如实上报（与 `hit_node_cap` 同一形状）。
4. **GUI 卡片**（§1.7）—— `--callgraph` 四格进 `gui.py`，与 R86-2 的二进制诊断卡片
   同构（配置往返 + `--selftest` 五件事）。
5. **产物级登记进 AGG**（黑帽 B4）—— `kernel_callgraph.json` 的 bytes/sha256 写进
   `AGG_r84.json`，让门 W 族能对它说「不」。
6. **终端告警升级**（黑帽 B1/B2）—— `ambiguous` 占比超过阈值、或截断比过小时，
   在 `format_report` 里显著提示，而不是安静地印一行。
7. **`--callgraph-top-n`** —— 30 是常量，语料不同该能调。

**仍然需要用户决断的两项**（R84 起挂着，本轮没动）：
* **C16-6 的六个从未提交的产物**是否提交？
* **`flow\`（archify 图册）**是否重建？（16.7 MiB 生成物，已 `.gitignore`）
