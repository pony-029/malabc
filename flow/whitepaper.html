01问题：为什么“代码转代码”走不通

MATLAB 是动态、统一管理内存的模型，嵌入式 C 则要求严格的静态布局和物理切片。只做“一行 MATLAB 对应一行 C”，会撞上四道墙：

墙表现根因
内存512×512 double = 2MB，塞进 256KB 当场 HardFaultC 需静态布局，MATLAB 不需要
搬运大数组在外存，CPU 只能访问片上没有 DMA 就是纯拷贝
算子同一个 sum，不同芯片不同指令语义与实现混在一个符号里
平台disp/fopen 在裸机上不存在语言运行时假设了 OS

核心判断：这四道墙都不是“翻译得不够好”，而是翻译缺少一个中间层——一层描述目标硬件是什么样，一层做“语义→实现”的选择。

03小脑：确定性的 90%

字节数 = prod(shape) × 8          # f64，与运行时 MLC_F64 一致
函数峰值 = 该函数内所有数组之和     # 保守上界，不做活跃期分析
形状未知 → 不计入峰值，但单独计数   # 不把"不知道"算成 0
为什么把“不知道”算成 0 是最危险的（点击展开真实案例）

如果预算把未知形状当 0 字节，报告会显示“tcm 用量 1%，非常宽裕” —— 而实际上有一批数组根本没被计入。等到运行时才发现溢出， 而那时报告已经绿了好几轮。

本仓在 mem_budget、mem_sections、isa_plan 三处都执行这条规则：未知单独计数，且不计入“够格”。

3.1 分段：从固定一段到任意段

{"sections": [
  {"name":"itcm","capacity_bytes":65536, "max_array_bytes":4096},
  {"name":"dtcm","capacity_bytes":262144,"max_array_bytes":32768},
  {"name":"ddr", "capacity_bytes":134217728}
]}

这条规则是被实测逼出来的。初版只用首段与末段，三段 profile 里中间段永远为 0—— 而它往往是 256KB 的 CPU 直连内存，最该被用上。“可配置段个数”在数据格式上成立、 在逻辑上不成立，等于没配。

3.2 口径修正：从“全工程累加”到“逐函数取最大”

口径numeric 语料 tcm 用量问题
全工程累加（旧）3112 B系统性高估：不同函数的数组不会同时存在
逐函数取最大（新）128 B仍低估跨调用链（A 调 B 时两者同时存在）

两个方向相反，必须分开算。新版只解决了“高估”那一半， 返回值里明确标 scope: per-function，不让读者误以为这是全局峰值。

04大脑：四信号

信号含义为什么不能猜
S1算子/形状组合无先例猜错会生成编不过的 C
S2同一段反复超限说明分流规则对它不适用
S3数组形状未知当 0 会让预算假通过
S4profile 没声明这个段/ISA生成器不知道往哪放
[大脑] 必须升级 2 项
  S3  有 9 个数组没有形状标注，峰值的下界算不准
      问：这些数组的实际维度是多少？或者它们能否改成由常量初始化？
  S4  profile 声明了 56 个算子想要的 ISA 变体，但头文件里没有对应符号
      问：这些算子在本板子上是「没有向量实现」还是「符号名不同」？

必须是“问题”而不是“警告”：警告只让人知道出事了，问题才让人知道下一步做什么。 “S4 缺失”是警告；“是没有向量实现，还是符号名不同”是问题——后者当场能回答。

05配置：profile 即物理事实

5.1 两份结构不同的 profile（这才是“通用”的证明）

profile段ISA 优先级用途
mcu_256k2 段（tcm 256KB + ddr 64MB）scalar → simd128简单 MCU
cortex_a_tcm_ddr3 段（64K+256K+128M）neon → sve → dsp + accel异构 SoC

只用一份 profile 验证“可配置”，永远不会暴露缺陷 —— 第一份往往是照着代码写的。 必须换一份结构不同的，才能测出“逻辑是否真的跟着配置走”。

5.2 可配 / 不可配的边界

可配不可配（口径）
段个数、段名、每段容量、单数组上限、ISA 顺序、加速器开关、算子覆盖、私有 ISA 规则字节数算法、形状未知不计入、四信号定义

右侧是口径。口径也配，等于允许每个项目自定义“什么算超限”——那就没有判据了。

06算子映射：三层路由

{"id": "OP-SUM", "matlab": "sum(x)", "c": "mlc_op_sum", "kind": "reduction"}
                                     ↑ 一个字段压了三件事

6.1 拆成变体选择 + 外部覆盖

候选 = [c_neon, c_sve, c_dsp, c_accel]   # 按 profile 的 ISA 顺序
      + [c]                              # 标量兜底，永远最后
选中 = 第一个在 mlc_ops.h 里声明过的
覆盖 = op-map 文件里声明的 c（优先级最高）
一个只有自证能抓到的 bug：优先级写反了

scalar 排第一位，next() 永远先命中它，simd/accel 永远选不上 —— 而输出表看起来完全正常（56 个算子“都有实现”）。

抓住它的是自证里那句“有 simd 实现时必须选中 simd”。这句话在现实中毫无用途 （那时还没有任何 simd 实现），它唯一的作用是描述“正确的行为应该是什么样”。

6.2 优先级：覆盖在最先

层来源优先级失败时
1项目映射文件 --op-map最高缺 why 判文件不合法
2平台配置（profile）次之ISA 未声明则跳过
3内置字典再次算子不存在则报错
4weak 桩兜底必须报桩比例

顺序必须是这样。配置的全部意义就是覆盖内置；把配置排在后面， 功能“看起来实现了却不生效”。

07私有指令集

7.1 条件必须结构化

写法问题
"is_vector && length % 128 == 0"没有任何东西会执行它；要生效只能 eval（注入面 + 无法静态校验）
{"min_len":128,"len_multiple":16,"require_align":64}三个字段各自可校验，语义清晰

7.2 判定用输入，不是输出

这里出现过一个完备性缺口。原先按输出数组判够不够格。对 sum(x)， 输出是标量（numel=1），于是：

⤵ OP-SUM  big_sum  numel 1 < min_len 128

也就是说所有归约类算子（sum/max/mean）永远不可能走向量实现 —— 而它们恰恰最该被向量化（树形归约）。改成取输入侧 numel 后：
✅ OP-SUM big_sum numel=1024 -> company_isa_vreduce

[isa] 规则 2 条 ｜ 命中 2 ｜ 够格 2 ｜ 退回通用 0
✅ OP-MATMUL  big_mmul  numel=16384 -> company_isa_mmul
✅ OP-SUM     big_sum   numel=1024  -> company_isa_vreduce

7.3 外部契约：dtype 是硬错误，不是精度

项规则为什么
dtype必须声明；非 f64 判错误本仓运行时是 f64；传 f32 会按 4 字节步长解释 8 字节元素 → 结果全错
align2 的幂且 ≤ 4096写错会让向量指令崩
header必填，不含 ..生成工程要能 include
why必填覆盖必须可审计

不要把 dtype 错位和浮点舍入混成一件事。舍入误差可以容忍； 类型错位必须立刻中止。如果工具只报“结果不一致”，人就会去调容忍度—— 而调容忍度对类型错位毫无用处。

09缺口看板

缺口偏差方向后果状态
跨函数调用峰值未算低估运行时溢出未做
生成器未接 profile/isa_plan—“自由转换”差最后一环未做
align 未注入变量声明—向量指令可能崩未做
多返回值段分配—段归属不明未做
weak 桩比例守卫—静默降级未做
数据流（读写关系）—段分配只能按大小猜未做

最危险的是 weak 桩。若 100 个函数里 60 个变成 stub， 生成的 C 编译通过、运行不报错、但什么都不做。必须加桩比例上限。

11设计原则

口径不可配，参数全可配

段容量可配，字节数算法不可配。口径也配，就没有判据了。

自证要测“本该做到什么”

只测“不出错”不够——优先级写反的实现照样输出正常的表。

用结构不同的配置验证可配

第一份往往照着代码写；换 2 段→3 段才测出中间段恒为 0。

“不比”“跳过”都要说出来

静默的“没判”与“判了且通过”输出一样，失效时无从分辨。

筛出 0 个时先证明筛子看过

“没命中”和“根本没看到”在计数上一样，原因毫不相干。

跨项目接口只交付纯数据

合并前后都不用改的接口，只能是不含策略的数据。
